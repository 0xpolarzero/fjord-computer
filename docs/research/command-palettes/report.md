# Great palettes win on plumbing, not matching

The fuzzy algorithm is the easy part. At Fjord's scale (a few hundred to a few thousand sessions, categories, actions and settings), a good matcher costs about **0.15–0.3 ms per keystroke**, so it could run about thirty times inside one 120 Hz frame. The best palettes pull ahead on everything around the matcher. The text field keeps focus while the arrow keys move a highlight in the list. Keys reach the input method before the palette sees them, so dead keys and accented letters survive. The list reuses a dozen fixed-height rows instead of rebuilding thousands. The ranking puts the right item first after one or two letters, through match tiers and remembered choices rather than a cleverer score. And the palette opens with its first frame already filled. The issue trackers of the open-source SwiftUI palettes (Ghostty, CodeEdit) are full of focus and lifecycle bugs, not speed complaints. The fastest Mac teams (Raycast v1, The Browser Company's Dia) kept this hot path in AppKit. For Fjord, that leads to five choices: an overlay inside the app window, SwiftUI for the static chrome, an AppKit text field and table for the parts that take keys and redraw on every keystroke, synchronous in-process ranking (tiers, frecency, per-query learning), and French-aware text folding. Add signposts that measure the time from a key press to the updated list on screen. A library matcher (ordo-one/FuzzyMatch) is a fair choice but not a requirement.

## Matching costs microseconds; the frame is spent elsewhere

The user's guess that the fuzzy algorithm is the hard part doesn't match the numbers. **FuzzyMatch scores about 33 million candidates per second** in its typo-tolerant mode and about 66 million in its Smith-Waterman mode on an M4 Max. Smith-Waterman is a classic alignment algorithm that finds the best way to line the typed letters up inside a title. At those rates, 10,000 items take roughly 0.15–0.3 ms on one thread, and highlighting 20 visible rows adds about 24 µs ([FuzzyMatch README](https://github.com/ordo-one/FuzzyMatch)). Zed measured **150 µs for a one-word query over 1,000 strings** when it moved its command palette to nucleo ([zed PR #54123](https://github.com/zed-industries/zed/pull/54123)). Even a 2016 C++ reconstruction of Sublime Text's matcher ranked 13,164 filenames in about 5 ms on a 2013 desktop CPU ([Forrest Smith](https://www.forrestthewoods.com/blog/reverse_engineering_sublime_texts_fuzzy_match/)). The one real trap is Foundation's convenience search. In the same benchmark, `localizedCaseInsensitiveContains` and `range(of:options:[.caseInsensitive,.diacriticInsensitive])` were 4–6x slower than a plain `lowercased().contains()` ([FuzzyMatch COMPARISON.md](https://github.com/ordo-one/FuzzyMatch/blob/main/Documentation/COMPARISON.md)). They are still fast enough for a few thousand short titles, but they only do substring matching, so they find things without ranking them well.

The bugs people actually filed sit elsewhere. Ghostty's palette lost its initial keyboard focus on macOS 26 beta 9. A "set focus on the next runloop tick" hack fixed it, and the bug came back with the Xcode 26.4 SDK ([#8497](https://github.com/ghostty-org/ghostty/issues/8497), [PR #11978](https://github.com/ghostty-org/ghostty/pull/11978)). Ghostty's palette also closed when the mouse moved over it under focus-follows-mouse ([#9533](https://github.com/ghostty-org/ghostty/issues/9533)). CodeEdit let ⌘W close the editor tab behind its open palette ([#1796](https://github.com/CodeEditApp/CodeEdit/issues/1796)), and needed a custom equality rule to stop its selection flickering while typing ([PR #1790](https://github.com/CodeEditApp/CodeEdit/pull/1790)). CodeEdit's one speed complaint, multi-second searches on a monorepo ([#1823](https://github.com/CodeEditApp/CodeEdit/issues/1823)), came from re-walking the disk on every query behind a fixed 200 ms debounce, not from the matcher ([OpenQuicklyViewModel.swift](https://github.com/CodeEditApp/CodeEdit/blob/fa2aebd86373211c78626074b53ab75010767575/CodeEdit/Features/OpenQuickly/ViewModels/OpenQuicklyViewModel.swift)). Rendering is the other place a frame gets lost. SwiftUI's `List` on macOS evaluates every row up front: one report measured about **2 s to show 10,000 rows**, and another saw 100% CPU for 50+ s ([TrozWare](https://troz.net/post/2024/swiftui_lists/), [HWS forum](https://www.hackingwithswift.com/forums/swiftui/swiftui-list-performance-with-row-count-2000/14259)).

So the real difficulty has five parts, roughly in order of how often teams get them wrong. First, focus and key routing between a text field and a list. Second, input-method safety: dead keys, accent popups and CJK composition. Third, a list that redraws only what changed. Fourth, a ranking whose top result is predictable and learns from use. Fifth, open and update without flashes or layout jumps. The fuzzy scorer itself comes after all five.

## The fastest Mac palettes keep the hot path in AppKit

A quick vocabulary note. **AppKit** is Apple's older Mac UI framework. You create view objects (`NSWindow`, `NSTextField`, `NSTableView`) and change them directly, so you control exactly what redraws and when. **SwiftUI** is the newer declarative framework. You describe the UI as a function of state, and the framework works out what changed. It is faster to write but harder to control. The two mix freely: `NSHostingView` puts SwiftUI inside AppKit, and `NSViewRepresentable` puts AppKit inside SwiftUI. Fjord already does both.

The pattern is consistent. Apps that own their renderer (Zed, Sublime) or stay in AppKit (Raycast v1, Dia, Xcode) control key routing and list redraws precisely. The SwiftUI palettes work for about a hundred commands, but they collect focus workarounds. Paulo Andrade notes that Spotlight's "keep typing in the search field while using up/down to move through results" is "currently not possible in pure SwiftUI" ([Paulo's Blog](https://pfandrade.me/blog/mac-assed-swiftui-app/)). Ghostty's Mitchell Hashimoto moved window-title handling "fully to AppKit" after the palette kept overwriting the title, and called the old SwiftUI approach "a relic" ([PR #7283](https://github.com/ghostty-org/ghostty/pull/7283)). Raycast moved off AppKit for cross-platform and hiring reasons, not speed, and paid for it in memory and IME work. That doesn't argue against native.

The window question has three answers, and only one fits Fjord. A **global launcher** (Raycast, Sol, Maccy) uses an `NSPanel` (a lightweight auxiliary window) with `.nonactivatingPanel` and `canBecomeKey = true`, so it takes the keyboard without bringing the app forward. It hides when it stops being the key window, the window that receives keystrokes ([Sol Panel.swift](https://github.com/ospfranco/sol/blob/main/macos/sol-macOS/views/Panel.swift), [Maccy FloatingPanel.swift](https://github.com/p0deje/Maccy/blob/master/Maccy/FloatingPanel.swift)). An **in-app child panel** (CodeEdit, probably Xcode) gets real behind-window blur and can extend past its parent window. The cost is key-window churn: the main window's titlebar dims, and menu shortcuts like ⌘W leak through to the window behind. An **in-window overlay** (Zed, Ghostty, and every web palette including Claude's) keeps the main window key and moves and resizes with it. Its cost is that you save and restore focus by hand. The Claude spec Fjord must match already settles this. The palette sits over a **50% black backdrop covering the window**, its top is computed from the window's height (`--cp-top`), and its width is `min(viewport − 80, 672)` (docs/design/spec/search-tabs-avatars.md §1.2). That is an overlay inside the app window, not a separate panel.

## Keys must reach the input method before the palette

This is where an AZERTY, French-UI user exposes shortcuts most often. In AppKit, a text field doesn't edit its own text. The window lends it a shared `NSTextView` called the **field editor**. Each key goes first to the input context (`interpretKeyEvents`). That step resolves dead keys and input-method composition. Only then does the field editor turn the key into either text (`insertText:`) or a named command: `moveUp:`, `moveDown:`, `insertNewline:`, or `cancelOperation:` for Esc ([Apple Cocoa Text Architecture](https://developer.apple.com/library/archive/documentation/TextFonts/Conceptual/CocoaTextArchitecture/TextFieldsAndViews/TextFieldsAndViews.html)). On AZERTY, `^` and `¨` are dead keys. While one is pending, AppKit holds a provisional character called **marked text** (`setMarkedText`), and `hasMarkedText()` returns true until the next key commits "ê" ([warp PR #14891](https://github.com/warpdotdev/warp/pull/14891)). The text field delegate method `control(_:textView:doCommandBy:)` receives those named commands only after the input method has had the key. So a palette that handles ↑, ↓, ↵ and Esc there gets composition safety for free: while a dead key or an IME candidate is pending, the input method consumes the arrows and Return, and the palette never sees them. DSFQuickActionBar is built exactly this way ([DSFQuickActionBar+Window.swift](https://github.com/dagronf/DSFQuickActionBar/blob/main/Sources/DSFQuickActionBar/private/DSFQuickActionBar%2BWindow.swift)). Overriding `keyDown` on the field doesn't work, because the arrow keys never arrive there ([QA1454](https://developer.apple.com/library/archive/qa/qa1454/_index.html)).

SwiftUI hooks run in the opposite order, and every SwiftUI palette has paid for it. An `.onKeyPress` on an ancestor view runs **before** the field editor. Returning `.handled` means the input method never sees the key. In Tinycast, ↑ stopped stepping through Japanese candidates and Esc closed the palette instead of cancelling the composition ([Tinycast #990](https://github.com/abue-ammar/tinycast/issues/990)). Maccy guards every key handler with `hasMarkedText()`. It also found that `onKeyPress` hides the key code, so ⌘, broke on non-English layouts, and it decodes `NSApp.currentEvent` with a layout-aware library instead ([KeyHandlingView.swift](https://github.com/p0deje/Maccy/blob/master/Maccy/Views/KeyHandlingView.swift)). The web library cmdk needed two releases to stop Enter and then all bindings from firing during composition ([cmdk #339](https://github.com/pacocoursey/cmdk/commit/f34d463)). Ghostty and CodeEdit route ↑/↓ through invisible zero-size `Button`s with `.keyboardShortcut`. That works, but it depends on SwiftUI focus timing, which has broken twice across macOS 26 SDKs ([Ghostty CommandPalette.swift](https://github.com/ghostty-org/ghostty/blob/291fd050b9e9c293c8adb6a140742649b7e42d3a/macos/Sources/Features/Command%20Palette/CommandPalette.swift)).

Fjord has a specific hazard here. Its app window installs an `NSEvent.addLocalMonitorForEvents(matching: .keyDown)` that sends keys to the Router and inbox key handlers (`AppWindow.watchKeys`). Like `onKeyPress`, a local event monitor runs before the field editor. Those handlers already bail out on `hasMarkedText()` (`AppWindowKeys.swift`, `RouterKeys.swift`), and the palette's keys should not join them. While the palette is open, the monitor should pass every key through untouched, except the ⌘K toggle, which Superhuman and Linear both make close the palette ([Superhuman](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/), [Linear changelog](https://linear.app/changelog/2024-04-24-editor-improvements)). The palette's own field delegate then handles the keys. The same reasoning picks the filtering trigger: filter in `controlTextDidChange`, which fires on committed text only. A pending `^` then never starts a filter pass, and the "ê" it becomes does. Focus restoration follows Zed's rule: save the previous focus when the palette opens, give it back before running the chosen action, so the action applies to what the user was looking at ([command_palette.rs L714-760](https://github.com/zed-industries/zed/blob/c403bc6af644cd0ab60c90045ac6dc3436218809/crates/command_palette/src/command_palette.rs#L714-L760)). Do it on the next runloop turn, as Ghostty and Tinycast both found necessary ([TerminalCommandPalette.swift](https://github.com/ghostty-org/ghostty/blob/291fd050b9e9c293c8adb6a140742649b7e42d3a/macos/Sources/Features/Command%20Palette/TerminalCommandPalette.swift)).

## Recycled fixed-height rows and stable IDs keep a keystroke inside one frame

Every fast list makes three choices: it renders only visible rows, all rows share a height, and each row's identity survives a re-filter. Zed's `uniform_list` "measures the first element and then lays out all remaining elements" from it, and renders only the visible range ([uniform_list.rs](https://github.com/zed-industries/zed/blob/c403bc6af644cd0ab60c90045ac6dc3436218809/crates/gpui/src/elements/uniform_list.rs#L1-L20)). VS Code gives every quick-pick row one of three fixed heights and caps file results at 512 ([anythingQuickAccess.ts](https://github.com/microsoft/vscode/blob/main/src/vs/workbench/contrib/search/browser/anythingQuickAccess.ts)). Slack's Quick Switcher went from 100 ms to a **median 12 ms render**. It fetched data when the switcher opened, capped the first view at 24 rows, and cut DOM nodes ([Slack Engineering](https://slack.engineering/a-faster-smarter-quick-switcher/)). On the Mac, the equivalent is a view-based `NSTableView`: fixed `rowHeight`, cells reused through `makeView(withIdentifier:owner:)`, and a non-animated reload. Animated diffable updates create throwaway cells, and on macOS 15 they skipped changed visible cells ([Apple Forums 706349](https://developer.apple.com/forums/thread/706349), [759384](https://developer.apple.com/forums/thread/759384)). CodeEdit shows the anti-pattern: it calls `reloadData()` on every SwiftUI update and builds a new `NSHostingView` per row with no reuse ([NSTableViewWrapper.swift](https://github.com/CodeEditApp/CodeEdit/blob/fa2aebd86373211c78626074b53ab75010767575/CodeEdit/Features/OpenQuickly/Views/NSTableViewWrapper.swift)). Ghostty's model gives every option a fresh `UUID()` each time it is rebuilt, so neither SwiftUI diffing nor `scrollTo` can follow a row ([CommandPalette.swift](https://github.com/ghostty-org/ghostty/blob/291fd050b9e9c293c8adb6a140742649b7e42d3a/macos/Sources/Features/Command%20Palette/CommandPalette.swift)). Fjord's spec suits a table well: **36 pt rows, 37 pt group headers and a 440 pt max list height** mean about a dozen rows are ever on screen.

Selection and pointer behaviour are details users feel without naming. The consensus is to **reset the highlight to the first result on every query change**, because the top result is what Return should run. This is cmdk's and VS Code's default ([cmdk index.tsx](https://github.com/pacocoursey/cmdk/blob/main/cmdk/src/index.tsx), [quickInput.ts](https://github.com/microsoft/vscode/blob/main/src/vs/platform/quickinput/browser/quickInput.ts)). When data changes under an unchanged query, the highlight should stay on the same item ID, since cmdk keys its selection by value. That case is real for Fjord, because a session's running dot flips while the palette is open. The Claude spec moves the selection on mouse move rather than tinting a hovered row. cmdk learned two refinements here. A pointer selection must never scroll the list "underneath" the user ([cmdk #3](https://github.com/pacocoursey/cmdk/issues/3)). Keyboard scrolling should go only as far as needed, and reveal the group header when the selection lands on a group's first row. Tinycast adds a third: ignore pointer "movement" until the pointer actually travels more than **3 pt**, so a list scrolling under a still mouse doesn't steal the highlight ([HoverArming.swift](https://github.com/abue-ammar/tinycast/blob/main/Tinycast/Palette/HoverArming.swift)).

The open is the last place to lose a frame. Zed blocks the main thread for **up to 4 ms** on open so the first frame already shows results, and up to 16 ms on Enter before results land, so typing quickly and pressing Enter still runs the right command ([picker.rs](https://github.com/zed-industries/zed/blob/c403bc6af644cd0ab60c90045ac6dc3436218809/crates/picker/src/picker.rs#L233-L245)). Raycast orders its window in at alpha 0 and waits for a drawn frame before showing it ([Raycast](https://www.raycast.com/blog/a-technical-deep-dive-into-the-new-raycast)). Motion should be minimal. Rauno Freiberg argues that an opacity-and-scale fade on a menu opened "hundreds of times a day" becomes cognitive burden ([rauno.me](https://rauno.me/craft/interaction-design)). Ghostty removed its palette animation because "lots of people complained" ([PR #9964](https://github.com/ghostty-org/ghostty/pull/9964)). Claude's own spec agrees: a palette opened from the keyboard uses `transition-none`.

## Rank in tiers, then learn per query

Matchers come in two families, and a palette over human-written French titles needs parts of both. **Subsequence matchers** require every typed character to appear in order. They reward word starts, camelCase and consecutive runs, and they return exact positions for highlighting. fzf, nucleo, Sublime, VS Code, Zed and cmdk all work this way. They handle "ns" → "New session" well, but return nothing for the typo "setings" ([fzf algo.go](https://github.com/junegunn/fzf/blob/master/src/algo/algo.go), [Zed matcher.rs](https://github.com/zed-industries/zed/blob/main/crates/fuzzy/src/matcher.rs)). **Approximate matchers** (Bitap/fuse.js, Damerau-Levenshtein) forgive typos but rank acronyms poorly. In FuzzyMatch's benchmark, the Bitap matcher Ifrit got 1 of 12 abbreviation queries right ([COMPARISON.md](https://github.com/ordo-one/FuzzyMatch/blob/main/Documentation/COMPARISON.md)). FuzzyMatch's edit-distance mode chains the two. It tries exact, then prefix with edit distance, then substring, then subsequence, then an acronym pass for 2–8-character queries, and it reports which `kind` matched ([DAMERAU_LEVENSHTEIN.md](https://github.com/ordo-one/FuzzyMatch/blob/main/Documentation/DAMERAU_LEVENSHTEIN.md)).

The scorer matters less than the ranking around it. Predictable palettes rank in **tiers** first and by score only within a tier. VS Code adds `1<<17` to any label-prefix match and `1<<16` to any other label match, so a prefix always beats a fuzzy hit ([fuzzyScorer.ts](https://github.com/microsoft/vscode/blob/main/src/vs/base/common/fuzzyScorer.ts)). Raycast's documented order is exact alias, then alias prefix, then fuzzy title, then subtitle and keywords, then frecency ([Raycast Manual](https://manual.raycast.com/search-bar)). Frecency is a blend of frequency and recency. Sol states the key rule outright: usage "can only reorder items of comparable match quality" ([Sol ui.store.tsx](https://github.com/ospfranco/sol/blob/main/src/stores/ui.store.tsx)). Zed is blunter: any previously used matching command beats every unused one ([command_palette.rs](https://github.com/zed-industries/zed/blob/c403bc6af644cd0ab60c90045ac6dc3436218809/crates/command_palette/src/command_palette.rs#L580-L667)). The feature users notice most is **query latching**: the app remembers which item was picked for the exact text typed. Alfred "latches the typed query phrase to the selected result", so two or three picks re-teach what "c" means ([Alfred Help](https://www.alfredapp.com/help/kb/understanding-result-ordering/)). LaunchBar ([LaunchBar Help](https://www.obdev.at/resources/launchbar/help/AbbreviationSearch.html)), Raycast ([changelog 1.40.0](https://www.raycast.com/changelog/1-40-0)) and Slack do the same. Slack keeps the last ten pick times per query, scores them in buckets (100 points under 4 h, down to 10 under 90 days), and gives half credit to other queries that reached the same item ([Slack Engineering](https://slack.engineering/a-faster-smarter-quick-switcher/)). Firefox publishes the cleanest formulas. Learned input history updates `use_count = use_count·0.9 + 1` and decays it ×0.975 per day. Frecency decays with a **30-day half-life** and is stored as a projected date, so nothing is rescored daily ([Firefox urlbar ranking](https://firefox-source-docs.mozilla.org/browser/urlbar/ranking.html)). Script Kit uses a 7-day half-life ([frecency/mod.rs](https://github.com/johnlindquist/script-kit-next/blob/main/src/frecency/mod.rs)).

French text needs explicit folding on both sides. Typing "e" for é/è/ê is the norm in a quick palette. FuzzyMatch folds the Latin-1 block and strips combining accents, so "cafe" matches "café". It also normalises curly apostrophes and non-breaking spaces to ASCII, which matters for French typography: "l’agent" and the space before "?" ([DAMERAU_LEVENSHTEIN.md](https://github.com/ordo-one/FuzzyMatch/blob/main/Documentation/DAMERAU_LEVENSHTEIN.md)). **œ and æ sit outside Latin-1**, so "oeuvre" probably won't match "œuvre" unless the app expands ligatures itself. The research didn't test this, and it deserves a unit test. If you fold strings yourself, keep a map from folded positions back to original positions, so highlighting still bolds the right characters. Zed found a related trap: strict smart-case filtering rejected "Editor: Backspace" for "editor: backspace". Use case only as a small score penalty ([fuzzy_nucleo.rs](https://github.com/zed-industries/zed/blob/c403bc6af644cd0ab60c90045ac6dc3436218809/crates/fuzzy_nucleo/src/fuzzy_nucleo.rs#L51-L128)).

On async results, the lesson is to avoid async work for in-memory data. cmdk, VS Code's command list and Ghostty all filter synchronously on every keystroke. Debouncing and throttling are only for slow sources ([cmdk index.tsx](https://github.com/pacocoursey/cmdk/blob/main/cmdk/src/index.tsx)). When a slow source exists, VS Code's numbers are worth copying. It cancels the previous request on every keystroke, applies fast results at once, merges slow results after a **200 ms** grace period to avoid flicker, keeps the scroll position, and shows the busy bar only after **800 ms** ([pickerQuickAccess.ts](https://github.com/microsoft/vscode/blob/main/src/vs/platform/quickinput/browser/pickerQuickAccess.ts), [quickInput.ts](https://github.com/microsoft/vscode/blob/main/src/vs/platform/quickinput/browser/quickInput.ts)). Zed debounces only when a search is already running, and tags results with an increasing search ID so stale results are dropped ([file_finder.rs](https://github.com/zed-industries/zed/blob/c403bc6af644cd0ab60c90045ac6dc3436218809/crates/file_finder/src/file_finder.rs#L1093-L1180)). The Claude spec already includes a slow path of this kind: a "Searching deeper..." spinner with a 150 ms delay.

## A recommended architecture for Fjord's ⌘K

**Placement and chrome.** Mount the palette as an overlay inside the app window: backdrop, surface, header and footer in SwiftUI, matching spec §1.2–1.6 exactly. These parts are static per keystroke, so SwiftUI costs little there, and Fjord's existing components and `--window-shots` workflow apply. Add `palette`, `palette-query` and `palette-empty` shots to `AppWindowShots.swift`. Inside the surface, embed one `NSViewRepresentable`, a `PaletteCoreView`, that owns an AppKit `NSTextField` and an `NSTableView` in an `NSScrollView`. SwiftUI never re-renders that subtree per keystroke. The palette model updates it directly. This is the hybrid split the evidence supports: AppKit for the field, key routing and list, and SwiftUI where nothing changes on every key.

**Keys and IME.** The field's delegate implements `control(_:textView:doCommandBy:)`. It handles `moveUp:` and `moveDown:`, `moveToBeginningOfDocument:` and `moveToEndOfDocument:` (⌘↑ and ⌘↓, as in cmdk), `insertNewline:`, `insertTab:` (the spec's "Actions" hint) and `cancelOperation:`. It also maps ⌃N and ⌃P. Filter in `controlTextDidChange`. While the palette is open, `AppWindow.watchKeys` returns every event untouched except ⌘K, which closes the palette. Register ⌘K as a menu key equivalent, which AppKit maps correctly across keyboard layouts, rather than matching characters in the monitor. On open, save `window.firstResponder` and call `makeFirstResponder(field)` directly. On close, restore the saved responder on the next runloop turn, first checking that it is still in the window, and then run the action. Fjord's `InboxSearch.pendingKeys` replay, which already re-types a dead key that started a search, shows the team has met this problem before. The same tests (dead `^` then `e`, the press-and-hold accent popup, ⌥-letter combinations on AZERTY) should gate the palette.

**Model and ranking.** A `@MainActor` `PaletteModel` builds a flat index when the palette opens, or keeps it current at idle as the store changes. Each entry holds a stable string ID (the session ID, `action.newSession`, `settings.appearance`), a kind, a group, a display title, a folded title (diacritics and case removed, œ→oe, æ→ae, curly quotes and NBSP normalised), keywords and a precomputed frecency value. Per keystroke, synchronously on main: score every entry, sort by `(tier, score × (1 + α·frecency) + kindPrior, learnedBoost, stableID)`, cap at a few hundred, then reload the table without animation and select row 0. The tiers are: exact title or alias, title prefix, word prefix or acronym, fuzzy title, keyword/category/subtitle, and typo-only. Usage reorders entries only within a tier. Persist two small maps. The first is `id → (count, lastUsed)`, decayed with a half-life of about 7 days for sessions and about 30 days for actions and settings. The second is `typedPrefix → id → useCount`, updated with Firefox's `·0.9 + 1` rule and decayed daily. Use the second as the query latch. The empty query shows the spec's "Recents" (by last opened) and a curated "Actions" order, Superhuman's default-score idea ([Superhuman](https://blog.superhuman.com/how-to-build-a-remarkable-command-palette/)). Only a slow source, such as a transcript-content search if one is added, runs as a cancel-per-keystroke `Task`. Its results are tagged with the query they answer and appended below the fast groups without reshuffling them, with the 150 ms spinner delay from the spec.

**Matcher choice.** ordo-one/FuzzyMatch 1.4.0 fits well. It is Apache-2.0, has no dependencies, supports macOS 14+, offers a zero-allocation `prepare` + `makeBuffer` + `score` path, and its `kind` output maps directly onto the tiers above ([FuzzyMatch](https://github.com/ordo-one/FuzzyMatch)). It declares `swift-tools-version: 6.0`. One assumption needs checking: SwiftPM compares each package's tools version with the installed toolchain, not with the root package, so a 5.10 root may resolve it as-is. That is my understanding, not something the research tested, and one `swift build` settles it. If Fjord must bump its own tools version, `swiftLanguageModes: [.v5]` keeps the app out of Swift 6 strict concurrency. The alternative is a hand-written tiered matcher of a couple of hundred lines: prefix and word-prefix checks, an fzf- or cmdk-style subsequence scorer with boundary bonuses, and a Damerau-Levenshtein fallback for queries of five or more characters. At a few thousand items either is fast enough, so choose on maintenance rather than speed.

**List.** Use a view-based `NSTableView`, `usesAutomaticRowHeights = false`, with `heightOfRow` returning 36 for results and 37 for group headers (headers as non-selectable rows, `floatsGroupRows = false`). Rows come from a reusable `NSTableCellView` that owns **one** `NSHostingView`, whose `rootView` is replaced with an `Equatable` row value: icon, status dot, title with highlighted ranges, and trailing meta or the ↵ icon when selected. This reuses Fjord's SwiftUI pieces while bounding SwiftUI's work to about a dozen visible cells. If signposts show it over budget, redraw those cells in AppKit. When the data changes but the query doesn't, reload only the affected rows by ID and keep the selection on its ID. Moving the mouse selects a row, never scrolls the list, and only counts after 3 pt of travel. Keyboard moves call `scrollRowToVisible`. Animate list height changes over 150 ms with the top edge fixed (spec §1.4). For accessibility, `NSTableView` exposes its rows natively. Post `.selectedRowsChanged` on arrow moves, and announce "{n} results available" as the spec's live region does ([Apple Forums 761728](https://developer.apple.com/forums/thread/761728)).

**Measurement.** Add `Palette open to first flush` and `Palette key to flush` signposts under the existing `com.amontlabs.fjord` subsystem and report them through `scripts/morph-timings.sh`. Hold them to the repo's own one-frame budget (docs/performance.md). No vendor publishes a latency budget, so these signposts are how Fjord will know it beats Claude's web palette rather than assume it.

## Conclusion

The "fuzzy algorithm" question breaks into two halves of very different difficulty. The scoring function is a solved, microsecond-scale problem with half a dozen well-documented reference designs. What users read as a smart palette is the ranking policy on top: tiers that keep a prefix match above a lucky fuzzy one, and a memory of what they picked for "se" last Tuesday. That policy depends on Fjord's own content (sessions that come and go, actions, rarely used settings), so no library can supply it. Write it, test it on real French titles, and tune it from usage.

The engineering risk sits at the seams between the text field, the input method, the window's existing key monitor and the list, the same seams where Ghostty and CodeEdit collected their bugs. Fjord starts in a good position: it already handles marked text in its Router and inbox, already replays dead keys, and already measures itself against a one-frame budget. Building the palette's core in AppKit and keeping SwiftUI to the parts that don't change per keystroke turns those habits into a structure. The palette will then look like Claude's ⌘K, and the signposts can show whether it is also faster.
