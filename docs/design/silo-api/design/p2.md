# Phase 2 implementation design

Build one signed engine installation per Mac user and channel, serve the canonical API from it, and make both apps socket clients.

This is an implementation design against the Phase 1 `silo-engine` extraction and `silo-api` wire types. It does not prescribe a second extraction or a second wire model. The contracts in [05](../05-engine-architecture.md), [95](../95-decisions.md), and the domain sections remain authoritative. Names and internal layouts introduced below are implementation choices, not additional public API methods. No code was changed for this design.

| --- | --- | --- |

An app starting, a handshake succeeding, or an SSH reconnect does not close those gates ([05 §10 OQ1–2, OQ24–25](../05-engine-architecture.md#10-open-questions)).

## 1. P2-silod

### 1.1 Files and ownership

Use the Rust workspace containing P1's crates. Suggested paths are relative to that workspace; adapt its root after merge without changing these boundaries.

| Create/change | Responsibility |
| --- | --- |
| `silod/Cargo.toml`, `silod/src/main.rs` | Modes, engine ownership, Tokio runtime on workers, AppKit on the initial thread |
| `silod/src/context.rs`, `paths.rs` | P1 context implementation; Silo channel paths and signed engine identity |
| `silod/src/macos/application.rs`, `main_thread.rs`, `service.rs` | NSApplication delegate/run loop; main-queue scheduler; SMAppService commands |
| `silod/src/socket.rs`, `session.rs`, `dispatch.rs`, `bridge.rs` | Private sockets, framing, authenticated sessions, canonical dispatch, SSH relay |
| `silod/src/process.rs` | Engine exit/restart coordination and session termination |
| `silo-engine/src/macos_computers/{engine,display}.rs` | Queue-confined VM ownership and native window presenter; replace the remaining Tauri window boundary |
| `silo-engine/src/{remote,channel,startup,system_shutdown}.rs` | Canonical Connections, channel names, engine startup, bounded termination |
| `silo-engine/src/maintenance.rs` | Autonomous upkeep timers owned by the engine, independent of client reads |
| `silo-install/` library and `silo-engine-install` executable | Shared per-user package selection, staging, installer journal, handoff, rollback. Both apps invoke the same packaged executable |
| `packaging/macos/{Info.plist,Entitlements.plist,LaunchAgents/...}` and Silo release/build scripts | Signed engine bundle, embedded resources, installation manifest, signature verification |
| Fjord `scripts/build-app.sh`, later installer integration beside `Sources/Fjord/Updater.swift` | Embed the identical engine distribution; invoke the shared coordinator |

`silod` depends on `silo-engine` and `silo-api`. The installer and thin native socket client depend on `silo-api`, not engine domain implementation. The Tauri UI must ultimately stop constructing an engine. Window presentation belongs with the engine's macOS adapter because its setup workflow uses the window too ([05 §§2.4, 3.6](../05-engine-architecture.md#36-the-engine-owned-vm-window-and-activation-policy); `src-tauri/src/macos_computers/engine.rs:1449`, `:1694`).

### 1.2 A shared signed installation, supplied by either app

Choose a canonical **per-user engine bundle**, copied intact from either application's distribution. This resolves the calling-bundle restriction without two competing registrations. Apple requires an agent plist in the calling bundle; its [GUI-less registration-app sample](https://developer.apple.com/documentation/ServiceManagement/updating-your-app-package-installer-to-use-the-new-service-management-api) supports invoking a bundle executable to register an embedded agent. Using that pattern for this shared per-user installation is a design choice requiring B-22 qualification.

```text
Fjord.app or Silo.app/
  Contents/Resources/SiloEngineDistribution/
    silo-engine-install                 # bootstrap copies coordinator into transaction staging
    Silo Engine.app/                    # sealed, independently signed candidate
      Contents/Info.plist
      Contents/MacOS/silod
      Contents/Library/LaunchAgents/org.silo.preview.engine.plist
      Contents/Resources/engine-manifest.json
      Contents/Resources/...            # P1 engine resources: msb, git, guest scripts

~/Library/Application Support/org.silo.preview/engine/
  Silo Engine.app/                      # canonical serving package
  staged/<transaction-id>/...
  rollback/<transaction-id>/...
  install.json                         # coordinator journal; never inside signed bundle

~/.silo/
  engine.lock                          # ownership held for silod's lifetime
  engine-install.lock                  # coordinator serialization, not engine ownership
  engine-owner.json                     # diagnostic instance/version/process record
  engine.sock
  engine/registry.sqlite3              # §2
  engine/update-resume.json            # §3
  desktop-remote/control.sock
```

Development uses the same structure under `org.silo.dev`, `~/.silo-dev`, a `Silo Engine Dev.app` name and `org.silo.dev.engine` label. All names come from `channel`, including the stable `~/.local/bin/silo-remote[-dev]` link. Existing Silo app-data/config/cache/log paths stay exactly as P1 resolves them; only engine-package storage is new ([05 §2.4 Paths](../05-engine-architecture.md#24-what-each-category-is-used-for); `src-tauri/src/channel.rs:1`, `:51`, `:73`, `:92`).

Important channel trap: current `channel::init` selects production **only** for `org.silo.preview`; `org.silo.preview.engine` would select development (`src-tauri/src/channel.rs:36`, `:45`). The sealed engine manifest therefore contains `channelIdentifier: "org.silo.preview"` or `"org.silo.dev"`, distinct from its `CFBundleIdentifier`. Initialize the P1 engine channel with that validated identifier. Do not derive it from Fjord's identifier, runtime environment variables, or unchecked command arguments.

Manifest v1 fields: `channelIdentifier`, `engineVersion` (SemVer), `engineBuild` (immutable release identity), `protocolMin`, `protocolMax`, `runtimeVersion`, `snapshotFormat`, `saveFormatVersion`, and a package content digest recorded by release tooling. Code signing seals the manifest and resources. Validate with Security.framework code-signature validation and the release's pinned engine signing requirement, including nested runtime signatures; a self-declared digest is not a trust check. Both apps ship the same Silo-signed engine. The local socket itself still trusts same-euid callers, with no signature authorization layer ([95 A-5](../95-decisions.md#2-technical-defaults-claude-veto-any); `src-tauri/src/macos_computers/engine.rs:243`).

Registration from **Fjord** and from **Silo.app** has identical steps:

1. Invoke the supplied coordinator with the embedded candidate's absolute path, as the logged-in user. Reject translocated sources and unsupported channels; never modify an application's signed bundle (`src-tauri/src/remote.rs:338`, `:349`).
2. Copy the validated coordinator and candidate into a private transaction staging directory and launch the coordinator there before a containing-app updater can replace its own bundle. The staged coordinator survives either client's exit/update; keep its executable and dependencies until it exits. Acquire `engine-install.lock` with `O_NOFOLLOW`, mode `0600`, exclusive flock. Inspect canonical package, installer journal, ownership lock and local socket before mutating registration.
3. If installation is needed, stage a whole validated bundle beside the canonical bundle. Invoke the **canonical engine bundle's** `Contents/MacOS/silod --service register`. This process calls `SMAppService.agent(plistName:)` from its own bundle and exits without constructing an engine. The parent Fjord/Silo process does not call `agent` against a plist in someone else's bundle.
4. `--service status`, `register`, `unregister` and `open-settings` are packaging commands, not socket API methods. Status maps `notRegistered`, `enabled`, `requiresApproval`, `notFound` to client installation state. Approval opens Login Items when requested. Never repeatedly register after user revocation. Apple's [register documentation](https://developer.apple.com/documentation/servicemanagement/smappservice/register%28%29) says registration bootstraps an agent but does not guarantee that it has started.
5. Prove readiness by connecting and completing `engine.handshake`; then read `updates.state.currentVersion`. `engine-owner.json` is a diagnostic cross-check, not an authorization token. B-30's first run reported enabled registration without a running job, so service status alone is insufficient ([probe B-30 initial run](../probes/macos.md#b-30-macos--partly)).

Keep the stable SSH forced command pointing at the canonical `silod`, never a client app. `--remote-bridge` only connects to `control.sock`; it never launches an engine or reaches `engine.sock`. `--remote-guest` retains its current guest transport purpose using canonical requests. The old AppImage helper is removed ([05 §8](../05-engine-architecture.md#8-mode-and-binary-mapping); `src-tauri/src/remote.rs:1748`, `:1804`, `src-tauri/src/channel.rs:98`).

### 1.3 LaunchAgent plist and restart policy

Production plist below is shipped sealed inside the canonical engine bundle. Generate the development variant at build time. `Info.plist` sets `CFBundleExecutable=silod`, `CFBundleIdentifier=org.silo.preview.engine`, `LSUIElement=true`; `silod` explicitly starts accessory. Sign the engine executable with virtualization entitlement; sign the runtime executable with its required hypervisor entitlement. No Apple Events entitlement is needed ([05 §3.3](../05-engine-architecture.md#33-entitlements-and-signing); `src-tauri/src/macos_computers/engine.rs:42`, `:243`).

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0"><dict>
  <key>Label</key><string>org.silo.preview.engine</string>
  <key>BundleProgram</key><string>Contents/MacOS/silod</string>
  <key>ProgramArguments</key><array><string>silod</string><string>--agent</string></array>
  <key>LimitLoadToSessionType</key><string>Aqua</string>
  <key>ProcessType</key><string>Interactive</string>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><dict><key>SuccessfulExit</key><false/></dict>
  <key>ThrottleInterval</key><integer>10</integer>
  <key>ExitTimeOut</key><integer>30</integer>
  <key>Umask</key><integer>63</integer>
</dict></plist>
```

The probe qualifies Aqua/Interactive and run-loop hosting on macOS 26.5, using `KeepAlive=false`; the conditional crash-restart policy above is a **new choice**, not probe evidence ([05 §3.2](../05-engine-architecture.md#32-launchagent-registered-with-smappservice-new); [probe Environment](../probes/macos.md#environment-and-method)). Successful deliberate shutdown exits 0 and stays stopped; crash/nonzero exit relaunches subject to throttling. Unconditional `KeepAlive=true` would undo explicit shutdown and race package replacement. Qualify `SuccessfulExit`, explicit restart after a clean stop, duplicate-instance exit 0, and logout behavior in the signed Dev harness. The 30-second launchd timeout leaves margin above the engine's 20-second session budget (`src-tauri/src/system_shutdown.rs:23`). Log through bounded files under `EnginePaths.app_log` and unified logging, not an expanded `$HOME` in a signed plist.

### 1.4 Detection and version rules: newest wins

No client starts a second engine on a connection failure. It asks the coordinator to ensure the canonical installation and service, then retries the socket. A second same-channel `silod` that loses `engine.lock` exits 0 without setup, migration, socket deletion, or VM creation ([05 §5.2](../05-engine-architecture.md#52-the-single-instance-rule); flock precedent `src-tauri/src/remote.rs:2014`).

| Comparison | Action |
| --- | --- |
| No canonical engine | Install candidate, register, verify handshake |
| Candidate older | Use installed/running newer engine; never downgrade it to match the app |
| Same version and build | Reuse; a client-only update has no engine handoff |
| Same version, different build/content | Refuse conflicting release identity. Production releases must bump engine version; development builds need a new prerelease identity to replace an engine |
| Candidate newer, compatible and save/resume ready | Perform §3 handoff, then both clients reconnect to the winning version |
| Candidate newer but unqualified runtime/save format or unsupported active guest capture | Keep the current engine serving; report the exact update blocker. “Newest wins” does not authorize losing running work |
| Client and winning engine have disjoint protocol ranges | Show `incompatible_version`; require a client update. Do not downgrade the engine or accept aliases |

Compare engine SemVer, not Fjord/Silo application version or bundle modification time. Strip build metadata from precedence; equal-precedence differing releases are a packaging error. Under the install lock, compare again immediately before handoff, so simultaneous Silo/Fjord launches cannot install an older candidate after a newer one. On each launch each app offers its candidate; no background scan of arbitrary applications is needed. The installer records the candidate offer for a later retry if existing work blocks replacement. Dev never consults the production feed (`src-tauri/src/updates.rs:238`, `:408`).

Normal detection uses handshake plus canonical `updates.state.currentVersion`, which already exists in the spec; do not add an ad hoc handshake `engineVersion` field. For a disjoint wire range, inspect the validated canonical manifest and engine ownership record and report incompatibility. Replacement of an incompatible running engine requires a coordinator built to speak that engine's canonical handoff protocol, otherwise it remains blocked until a suitable installer is supplied. No v5 compatibility bridge is retained ([05 §4.2 G](../05-engine-architecture.md#g-capabilities-and-version-negotiation), [60 §5.2](../60-connections-settings-services.md#52-methods); `src-tauri/src/updates.rs:46`, `src-tauri/src/remote.rs:2166`).

### 1.5 Main thread, VM queues, and native windows

Initial thread: validate bundle identity and lock ownership; create `NSApplication`, delegate and an autorelease pool; set accessory; start worker runtime/bootstrap; enter `NSApplication.run()`. Do not put `#[tokio::main]` on the entry point and then block that executor in AppKit. Bootstrap follows [05 §7](../05-engine-architecture.md#7-engine-startup-sequence-for-reference-by-the-other-sections), including launch-only migration and existing recovery order. Bind listeners after minimum state is initialized; during recovery allow handshake, engine state and diagnostics, but hold changes behind recovery admission. Start-at-launch runs last. Existing setup order is `src-tauri/src/main.rs:291`; recovery is `src-tauri/src/startup.rs:153`, `:227`.

Install upkeep on the worker runtime after recovery, with no client required: initial design intervals are 30 seconds for pending secret revocations and port repair, and one hour for stopped-computer log expiry. Preserve existing one-pass guards, hidden try-gates and the per-computer hourly cleanup cap; skip blocked work and retry on the next tick, never stack timer tasks. Suspend mutating upkeep during update/shutdown ownership. These intervals require B-36 measurement, not owner approval ([05 read-triggered maintenance](../05-engine-architecture.md#read-triggered-maintenance); `src-tauri/src/secrets.rs:753`, `src-tauri/src/runtime.rs:2700`, `src-tauri/src/network.rs:737`). Test recovery/retry with all clients disconnected.

`MacContext.main_thread()` enqueues closures on the AppKit main queue. Preserve P1's `MainThread::run` contract and the existing pending/running/abandoned behavior: a timed-out pending closure must not perform a late mutation, and a started closure must report its outcome. Undo/resume closures are patient. Never wait synchronously on the AppKit thread for itself or a VM callback (`src-tauri/src/macos_computers/engine.rs:142`, `:185`, `:1020`).

Implement the queue choice from [05 §3.4](../05-engine-architecture.md#34-main-thread-and-the-appkit-run-loop): a dedicated serial queue per VM for creation, validation, installer, lifecycle, save/restore, sampling and delegate callbacks; AppKit main queue for views/windows. Current `SLOTS` and `MachineDelegate` are main-thread confined (`engine.rs:1`, `:46`, `:65`, `:81`, `:554`), so changing the constructor alone is incorrect. Move the entire VM slot and delegate confinement together. A queue-owned `VmSlot {computer_id, generation, vm, delegate, installer, save_restore}` is accessed only through queued commands. Worker-facing `VmHandle {computer_id, generation, queue}` transports plain results via channels. Keep the unsafe Objective-C boundary private; do not make framework objects generally `Send`/`Sync`.

The display bridge narrowly retains the queue-owned VM for the main-thread `VZVirtualMachineView` attachment, following the B-1 harness. No other main-thread VM operations are allowed. Views never cross to worker threads. If the objc2 binding cannot express the queue confinement, extend that adapter/binding rather than scatter unchecked `Send` impls. B-1 confirms this arrangement on one host version; qualify all supported hosts before making it the default ([probe B-1](../probes/macos.md#b-1--confirmed)).

Main-thread `WindowRegistry: HashMap<ComputerId, DisplayWindow>` holds retained `NSWindow`, view, window/toolbar delegates, VM generation, setup ownership and optional client attachments. `display.show` focuses an existing window or creates a native 1440×900 window, minimum 640×400, resizable; attaches the view to the content layout guide; enables system keys and automatic display resizing; makes the view first responder. Port toolbar actions and subtitles unchanged. Closing detaches the view and clears `displayOpen`, never stops the VM (`src-tauri/src/macos_computers.rs:2209`, `:2229`; `engine.rs:1328`, `:1432`, `:1478`, `:1616`; [30 §5](../30-macos-computers.md#5-display)).

Set regular **before** showing the first VM/setup window; return accessory after the last window has detached and closed. Count windows, not clients or running VMs. Check the setter's boolean result and report failure without claiming the transition happened. Retain delegates because Cocoa references them weakly. Duplicate close callbacks and stale VM generations do nothing. Recovery setup uses a toolbar-free window and its existing input monitor; refuse user/API close while setup owns it. That monitor is setup protection, not a public screen lock (`engine.rs:55`, `:71`, `:1694`, `:1743`; [95 A-8/A-21](../95-decisions.md#1-owner-decisions)).

A local macOS window is shared engine presentation, one per computer. `engine.disconnect` removes the caller's attachment but does not close a window used by setup or another client. Close an automatically client-attached window only after its last attachment leaves; explicit window close remains the global `display.close` behavior. Linux and remote macOS viewers remain independent client connections, never embedded engine views ([05 §5.3/§6](../05-engine-architecture.md#53-two-clients-at-once-silos-ui-and-fjord-per-client-vs-engine-state); 95 A-28). The follow-up B-3 observed Foreground/UIElement classifications, not screenshots of Dock/⌘-Tab or login-window behavior ([probe follow-up B-3](../probes/macos.md#b-3--confirmed-for-app-classification)).

When the engine has a Dock menu, its Quit action closes VM windows and returns accessory; it does not silently kill the VM owner. Explicit computer stops and engine shutdown remain API actions. AppKit session termination and SIGTERM use the bounded engine shutdown path below.

### 1.6 Socket, session, dispatch, and handshake

`engine.sock` is `channel.state_dir(home)/engine.sock`; `control.sock` remains under `desktop-remote`. Set umask `077` before creation. Verify state directory euid ownership and `0700`, socket `0600`, lock files regular/euid-owned `0600`, no symlink traversal. Open locks `O_NOFOLLOW | O_CLOEXEC`; never inherit engine ownership into a runtime child. Reuse and harden existing private-directory checks (`src-tauri/src/runtime.rs:861`; `src-tauri/src/remote.rs:133`, `:2014`, `:2047`). Detect overlong macOS `sockaddr_un` paths and return a diagnostic, without inventing an alternate socket location.

Only the lock holder may remove a stale socket: `lstat` must show an owned socket, and connect must fail `ECONNREFUSED`. A successful connect means another owner; any other error is a refusal to unlink. On shutdown unlink only the socket inode this process bound, before releasing `engine.lock`. Apply `getpeereid(fd)` immediately after every Unix accept, before parsing any bytes, requiring peer effective UID equal to engine effective UID. Failure closes the connection. Apply to both sockets; the bridge executable is the same user. This is new protection, absent from current source ([05 §4.2 A/C](../05-engine-architecture.md#a-local-clients-on-a-unix-socket-without-the-connections-gate); `src-tauri/src/remote.rs:2034`, `:2069`).

Session structures, internal only:

```rust
Session { id, peer_euid, origin: Local | Bridge, protocol, caller_id,
          pending_ids, writer, subscriptions, attachments, closed }
Caller { client_id, origin, device_id, session_id }
RequestContext { caller, operation_id, start_condition, job_id }
MethodSpec { name, class: Read | Change | Stream, kind, handler }
```

One reader decodes 4-byte BE length + UTF-8 JSON, rejecting lengths above 4 MiB before allocation. One writer owns the output byte stream, so concurrent replies/events never interleave bytes. Replies may be out of request order and echo P1 `id`; exactly one of result/error is present. IDs are unique for the whole connection, not just while pending. Bound remembered IDs at 65,536 and end that session for reconnect at the limit rather than retain an unbounded set. Use P1 validation and errors; unknown methods return `unsupported_remote_operation`. No legacy error string or preamble is written ([05 §4.2 B](../05-engine-architecture.md#b-a-persistent-multiplexed-connection); framing source `src-tauri/src/remote.rs:546`, `:649`; retired preamble `:559`, `:578`).

Initial limits, to measure with B-35: 64 local management sessions, 64 bridge management sessions, 32 in-flight requests per session, a global 64 active read/short-dispatch workers, and 192 bridge streams. Jobs return after durable admission, so long work does not hold a request-worker permit; existing gates and domain limits control it. Replies use a bounded reliable queue (64 frames, 8 MiB); write timeout 30 s closes a stalled session. Events have separate bounded queues (§2). Never await socket I/O while holding a domain/gate/database lock. Full limits give a canonical `busy` reply when a request ID is available; otherwise close before handshake. Reserve lifecycle control capacity for `engine.state`, job get, abort and shutdown so normal reads cannot starve recovery. First handshake deadline is 15 s, matching current first-frame protection (`remote.rs:2086`, `:2087`, `:3376`).

Handshake is the first request on either socket. Negotiate the highest overlap of the P1 protocol range; no overlap returns `incompatible_version` with P1's version/appVersion diagnostics and closes. Local handshake allocates a fresh opaque UUID `clientId`; it cannot be supplied by the client. Return device identity/name, chosen protocol, and the actual registered canonical capability names. Bridge handshake requires Connections enabled, is exempt only from target `deviceId` matching, and may restrict the provided `sshKey`; it returns no local clientId. Allocate an internal caller UUID for a bridge session so requester-only setup progress can target it, without adding that field to the bridge handshake. Each later bridge request must match the negotiated version and owner device ID and pass Connections/admission checks ([05 engine.handshake](../05-engine-architecture.md#enginehandshake); `remote.rs:2161`, `:2179`, `:2203`, `:2242`). Generate capabilities from the same dispatcher descriptors that serve requests, omitting unfinished/retired methods, including `repository.push` (`remote.rs:261`).

Dispatch order:

1. Validate session, envelope, canonical name and typed params. Derive caller from authenticated session; ignore no client-provided claims of authority.
2. For local requests with a remote `deviceId`, route via the engine's Connections adapter. Bridge requests target this owner only, never a second-hop relay. Local reads work with Connections off.
3. Check method policy and current admission. Reads remain available while preparation holds changes; abort and required lifecycle controls bypass that change hold deliberately.
4. For Change, use transport idempotency and start deadline (§2.2). For a job, persist acceptance and return `{jobId}` before starting its worker; install the gate start condition in that worker, not only in the socket task.
5. Invoke the extracted domain method with `EngineContext` and `RequestContext`. Domain code obtains its gate, rechecks immutable computer identity/state and admission, executes, and commits its result. Never hold one global dispatcher mutex across all operations.
6. Map typed engine errors into P1 `ErrorCode`; complete through the job registry where appropriate. Client pickers/launchers remain client work. No `runtime.*`/old command aliases or legacy decoders survive ([95 §3](../95-decisions.md#3-amendments-owner-2026-10-13-later); old dispatcher `remote.rs:2201`).

Raw `guest.ssh` and `macos.display.stream` use dedicated sessions. After handshake and a sole stream request, write its framed success then switch that connection to raw duplex bytes; reject upgrade with other requests/subscriptions pending. `events.subscribe` stays **framed** despite its Stream budget class (§2.4). This preserves the byte-stream methods without corrupting multiplexed management framing (`remote.rs:2090`, `:2806`, `:2852`; [05 §4.1 Stream upgrade](../05-engine-architecture.md#41-todays-bridge-protocol-protocol-version-5-as-implemented)).

### 1.7 Shutdown

Keep client disconnect separate from engine lifecycle. `engine.shutdown` takes a durable job; concurrent equivalent shutdowns attach to that job. A conflicting reason/options request is `busy`. The lifecycle controller retains `phase`, `generation`, `sessionEnding` and `updatePending`, projected by `engine.state`; `engine.shutdown.changed` retains its specified `{shuttingDown}` payload ([05 §6](../05-engine-architecture.md#6-quit-update-and-shutdown-for-an-engine-that-outlives-clients); `settings.rs:539`, `:557`, `:924`).

For explicit stop: cancel startup, close admission, cancel waiters, drain transfer cleanup while guest connections still exist, take the device gate, close SSH/viewers, stop local macOS machines while AppKit keeps running, stop/verify exact Linux identities, flush settings, close tunnels, persist shutdown completion, enqueue final event/reply, briefly drain writers, remove listeners and exit 0. Retain current parallel Linux stops and worker flock. Failure for reason user preserves the engine and reopens admission; it does not restart computers already stopped. Do not stop another device (`runtime/shutdown.rs:13`, `:61`, `:83`, `:96`, `:132`, `:238`; `settings.rs:879`, `:920`).

For update with `stopComputers:false`, require a completed held update transaction and run §3's release path, never `stop_local_computers`. Other false requests are refused while any macOS VM remains owned; detached Linux machines may remain. SIGTERM and AppKit logout/shutdown enter `sessionEnd`, no prompt, earliest deadline wins, default 20 s, never cancel exit after a stop/save failure. When already prepared for an update, termination must preserve/release the saved set rather than guest-shutdown it. At exit disable ordinary cleanup that would overwrite update state. `ProcessControl.restart` schedules orderly termination/relaunch; it must not `exec` while live VZ objects or ownership locks remain (`settings.rs:981`, `:1026`; `updates.rs:684`).

P1's wire types remain in `silo-api` ([05 job contract](../05-engine-architecture.md#job-contract); source queue `operation_gate.rs:94`, progress `transfer.rs:103`).

Use SQLite through `rusqlite`, with one database owner on a blocking worker and short serial transactions. File: `<state dir>/engine/registry.sqlite3`, parent `0700`, database/WAL/SHM `0600`. `PRAGMA user_version=1`, `journal_mode=WAL`, `synchronous=FULL`, `fullfsync=ON`, `foreign_keys=ON`, bounded busy timeout. Verify the settings took effect. Never place this database on a network share or in the app bundle.

Choice evidence: [SQLite WAL](https://www.sqlite.org/wal.html) supplies transactional commit and local readers; [SQLite synchronous/fullfsync](https://www.sqlite.org/pragma.html#pragma_synchronous) documents durability and macOS full sync; [rusqlite](https://docs.rs/rusqlite/latest/rusqlite/) supplies Rust transactions and a bundled SQLite option. Prefer these to building a generic JSON transaction log. Pin a maintained crate/SQLite version in Cargo.lock at implementation and check upstream advisories and licenses ([rusqlite manifest](https://github.com/rusqlite/rusqlite/blob/master/Cargo.toml), [SQLite public-domain policy](https://www.sqlite.org/copyright.html)). The library stores only product policy. This does not encrypt same-user data or guarantee durability on failing storage; the OS-user threat model is [95 A-5](../95-decisions.md#2-technical-defaults-claude-veto-any). Measure commit latency and WAL growth in B-37.

Schema v1, logical columns:

| Table | Columns and constraints |
| --- | --- |
| `jobs` | `job_id TEXT PRIMARY KEY`, `method`, `params_fingerprint`, `domain_id`, `computer_id?`, `requester_client_id?`, `audience`, `accepted_order INTEGER UNIQUE`, `accepted_at_ms`, `started_at_ms?`, `finished_at_ms?`, `state` (`waiting/running/finished/acknowledged`), `outcome_json?`, `recovery_kind`, `recovery_ref?` |
| `request_claims` | `operation_id TEXT PRIMARY KEY`, `method`, `params_fingerprint`, `job_id?`, `state` (`accepted/started/finished/expired/uncertain`), `response_json?`, `accepted_at_ms`; FK to jobs when applicable |
| `notices` | `key TEXT PRIMARY KEY`, `computer_id?`, `notice_json`, `updated_order` |
| `meta` | allocation counters/schema metadata, including next accepted order |

Outcome JSON is exactly `{result: ...}` or `{error:{code,message,...P1 diagnostics}}`, not a flattened domain result. Keep an acknowledged job's identity/fingerprint tombstone but delete its outcome and requester details. `operations.job.get` treats that tombstone as `not_found`; its absence from `unacknowledgedJobIds` is durable. Tombstones prevent reuse of client domain IDs from re-executing completed work. They are not retained outcomes. Do not retain raw secret request params in generic claims; fingerprint deterministic canonical JSON with a private per-install keyed digest when params contain secrets. Keep the digest key outside bundles, private to the user. Recovery uses existing domain journals, not replay of generic captured arguments.

Use a durably inserted UUID for `job:<uuid>` and a database uniqueness constraint, retrying a collision before acceptance. No process-local counter becomes a job ID. Store monotonic accepted order transactionally for deterministic discovery. Gate IDs stay `u64` process-local admissions, never durable identities (`operation_gate.rs:249`; [05 §4.2 E items 1–2](../05-engine-architecture.md#job-contract)).

Acceptance transaction: allocate/find job, compare fingerprint, insert transport claim if supplied, commit **before** returning `{jobId}` or launching work. A repeated matching domain ID attaches to that job; a changed fingerprint is `internal` with an identity-reuse message, matching current refusal (`remote/operations.rs:34`, `:117`; `host_push_operations.rs:202`). An acknowledged ID never starts again; return its existing job identity, whose outcome get is `not_found`. Clients must use a new ID for new work.

Completion transaction: write terminal outcome and finish time once, update claim state, commit, then publish `operations.job.finished`. Repeated identical finish is harmless; conflicting finishes log a programming error and preserve the first terminal value. A crash after commit but before publish loses only delivery. On commit failure, do not publish success or perform a planned restart. Keep the result pending in memory, refuse new mutations, retry persistence and surface a storage error. Generic persistence cannot make an arbitrary domain side effect and its result atomic; existing journals must close that crash seam. If neither journal nor state can prove an outcome after a crash, reconcile as an explicit uncertainty error rather than fabricate success.

Get/ack semantics are serialized at database transactions: get can return the pre-ack outcome or `not_found`; acknowledge commits deletion before returning null. Unknown/already-acknowledged acknowledge succeeds, waiting/running acknowledge returns `busy`, persistence failure returns `internal` and preserves retention. Recovery consults acknowledged tombstones before reconciling domain history; an export/push result still visible in its domain cannot recreate a consumed generic outcome. Any authorized client can acknowledge globally, only after showing the outcome. Reading, closing a viewer, notice clearing and domain `exports.dismiss` do not acknowledge jobs ([05 operations.job.get/acknowledge](../05-engine-architecture.md#operationsjobget); [20 exports acknowledgement](../20-checkpoints-exports-preparation.md)).

No age expiry, one-hour prune, or 256-outcome eviction. Load retained outcomes on startup and expose IDs through `operations.list.unacknowledgedJobIds` even if their requester disconnected. Cap the in-memory cache, not persisted outcomes. Since the wire has a 4 MiB cap and `operations.list` has no paging contract, reserve a conservative byte budget at acceptance for future discovery IDs; refuse additional jobs with `busy` before that projection can exceed the cap. Never silently truncate discovery. Individual outcome size is bounded at each domain boundary before effects where possible. If any existing final result can exceed a get frame, resolve its API representation before enabling that method; do not discard it ([10 §6](../10-computers-lifecycle.md#6-operations); [05 §4.2 B/E](../05-engine-architecture.md#job-contract)).

In-memory `ActiveJob` holds a shared cancellation token, current gate IDs, cancellation policy, attached execution owner and optional domain handle. Explicitly pass the `JobId` into each gate builder; don't infer it from a thread-local caller after crossing Tokio/spawn_blocking. Running jobs with an authoritative recoverable domain journal retain their job identity and attach to that recovery worker. Queue reconstruction is from attached recovery workers only, not a claim that all old processes continue. Save engine-launch migration completion before its restart and reconcile a crash before that commit from the migration journal ([05 §10 OQ25](../05-engine-architecture.md#10-open-questions)).

### 2.3 Sequenced bounded events and resync

`Subscription {id, session, topics, sources, next_seq_by_source, bounded_queue}`. ID is opaque and fresh on subscribe. Match catalogue event names or `domain.*`; unknown selectors are refused rather than subscribing silently to nothing. Subscribe registers filters and enqueues its response before events can be written. Omitted deviceIds means local only; explicit device IDs are validated and deduplicated. Unsubscribe is idempotent and connection close disposes all its subscriptions ([05 events.subscribe/unsubscribe](../05-engine-architecture.md#eventssubscribe)).

Assign `seq` starting at 1 for each `(subscription, deviceId)` after topic/audience filtering. It increments for every matching event, including an event that cannot be buffered, not for unrelated topics. Local-only subscriptions have one sequence. Multi-owner subscriptions retain each owner's counter, keyed by deviceId; independent engines cannot share a global counter. This makes the spec's “per subscription” order concrete for its source-engine envelope without changing fields. P1 schema fixtures must document this source qualification ([05 §4.2 D](../05-engine-architecture.md#d-pushed-events-a-subscription-method-and-an-event-envelope)). Never reuse an old subscription ID after owner restart.

Initial limits: 256 events and 8 MiB encoded bytes per subscription, 16 subscriptions and 16 MiB aggregate event backlog per session. These are tunable implementation constants, not observed capacities. Publication is nonblocking: enqueue or mark that session lost. On overflow close the subscriber session immediately; do not block VM callbacks, allocate indefinitely, emit an invented gap event, or silently drop the final event while waiting for a later event to reveal the gap. A dropped session forces reconnect/resync; jobs/notices survive that loss. Independently, clients detect any nonconsecutive seq, reject duplicate/stale seq, and resync on owner disconnection. Shutdown/reply delivery uses its own queue, so an event flood cannot hold the engine hostage. Measure overflow, memory and latency under several slow local/SSH consumers ([95 A-4](../95-decisions.md#2-technical-defaults-claude-veto-any); 05 OQ12–13).

Changed events carry actual state, not hints. Build projections from the same state used by their read methods, after a committed mutation, following [05 catalogue](../05-engine-architecture.md#event-catalogue). Queue events carry the extended queue; progress retains source payloads field-for-field; setup progress is requester-only; durable finished outcomes remain discoverable by all authorized readers. Setup failure's final diagnostic progress precedes finished. Do not write byte streams into `operations.job.progress`; guest exec maintains its separate output sequence (`runtime.rs:3586`, `:4211`; `macos_computers.rs:667`, `:707`; `transfer.rs:1398`).

The snapshot/event race needs an explicit seam. Keep each domain's **published projection** and its event publication ordered under a short projection lock. Internal `Projection {revision: u64, value}` gives every domain an ordering revision, including domains whose wire payload has none. Reads used for subscription resync clone that projection and enqueue their response in the same ordering boundary as that session's domain events. A producer must update the projection before enqueueing its event. Perform slow runtime sampling outside the lock with a captured base revision; discard/retry the observation if a later mutation changed that revision before commit. Preserve existing wire revision numbers too. The lock never covers VM/SSH/fsync or socket writes. A per-session ordered outbound mailbox preserves barrier order even with separate byte-budget accounting for responses and events.

Client resync algorithm:

1. Mark the affected source stale; invalidate that subscription generation. Unsubscribe and create a fresh subscription (or reconnect if the transport closed).
2. Subscribe before reading, then issue each affected domain read on the **same framed owner session**. A new subscription's initial expected seq is 1. Read operations, retained job IDs and notices as needed, not only computers.
3. While each read is pending, do not apply that domain's events to trusted UI state. The response frame is its ordering barrier: replace the snapshot; ignore preceding events for that domain; apply only subsequent events in sequence. Track sequence for ignored frames too. A second gap repeats resync.
4. Job finished events lost before the barrier are recovered by list/get; no event replay is assumed. Only after all selected domains have crossed their barriers is the source fresh.

This avoids adding a public cursor/snapshot method that P1 does not define. Test it with state mutation before capture, between capture/enqueue, and after response enqueue. A general async read that returns a stale independently sampled value cannot act as this barrier. Domains without a safe published projection must be fixed before their pushed subscription is advertised. This requirement follows [95 A-4](../95-decisions.md#2-technical-defaults-claude-veto-any), not an assumption that subscribing and reading automatically produce a consistent snapshot.

### 2.4 Retained notices and the remote stream

Notice production writes/upserts the exact `Notice` by key transactionally, then publishes `notifications.notice`. Persist notices in the registry across restart as this design's B-29 default; no age expiry or arbitrary key eviction. Latest replaces earlier. Successful deletion removes all keys for `computerId` transactionally before publishing `notifications.cleared {computerId}`. `notifications.list` reads without consumption. Engine applies its existing operation-duration/failure rules, but no focus/category/OS-authorization filters and no OS delivery; only Fjord renders engine notices. Silo UI can show job/domain outcomes, not present retained engine notices ([60 §4.2](../60-connections-settings-services.md#42-engine-shape-retained-notices-that-fjord-renders); `notifications.rs:55`, `:118`, `:281`, `:358`). Bound list frame size at notice production; storage failure preserves the old key and reports the failure. B-29 must test cardinality and startup notices with all clients absent.

Keep one framed SSH session per `(local client session, remote owner)`, reused for that client's subscriptions and remote management requests. Handshake, then canonical `events.subscribe`. Convert the owner connection's management permit to one Stream permit atomically on its first subscription, retaining the 192-stream cap; additional subscriptions on that session do not take extra permits. Do not switch its bytes to raw. The relay is duplex framed: read/get/ack/unsubscribe and job-start requests use this same session. This is essential both for §2.3 snapshot barriers and for requester-only setup events to reach the bridge caller that started the job. It still passes Connections authorization on every request and while streaming (`remote.rs:3376`, `:3390`, `:2098`). Do not introduce a second event framing protocol or poll remote state every 10 seconds.

The controller's engine replaces owner subscription ID with the local client's subscription ID and preserves source deviceId, sequence, payload, and ordering. Request IDs use a relay mapping. Relay remote domain read replies through the same ordered path as events; never route resync reads through separate short SSH sessions. `(deviceId, jobId)` always targets owner storage, including acknowledgement; the controller holds no authoritative job outcome copy. Backpressure overflowing the local consumer ends its relay; owner overflow/loss closes the downstream client session too, making resync unavoidable. Do not splice a new owner subscription with reset sequence into an existing downstream ID. Reconnect with fresh IDs; expose Connections health through its catalogue projection ([05 §4.2 E item 6](../05-engine-architecture.md#job-contract); `remote.rs:1490`).

`--remote-bridge` removes the old preamble and one-shot parser and copies the canonical session to control.sock only. No shell noise decoder remains. Keep stdout exclusively for framing and put diagnostics on stderr. Noninteractive shell setup that writes stdout now fails visibly; fix that environment rather than retain v5 compatibility (`remote.rs:559`, `:1748`, `:1785`; [95 §3](../95-decisions.md#3-amendments-owner-2026-10-13-later)). Stream revocation on Connections off ends event sessions; already admitted jobs keep their owner. Connected-key revocation integration remains P3-connections, not evidence supplied by P2.

1. **Durable outcome tracer:** one fake long job, accept/get/finish/list/ack, exact P1 JSON fixtures. ### 3.3 Sequence

1. **Stage while guests run.** Shared coordinator validates signatures/channel/version/compatibility and stages the new package with the old package retained. If engine version is unchanged, finish the client update without any engine call. Do not replace the canonical bundle while serving ([05 §6.2](../05-engine-architecture.md#62-client-quit-and-engine-update-are-separate-contracts)).
2. **Accept prepare job.** Serialize with any shutdown/update; return durable job ID. Cancel/wait startup; acquire update admission plus backup/GitHub/secrets guards, then device gate in the established order. Refuse active/queued ordinary work before taking a destructive step. Keep state/get/abort requests available. Flush engine settings, pause transfer admission and drain cleanup before disconnecting guest transports (`updates.rs:806`, `:813`, `:817`, `:827`; `runtime/shutdown.rs:83`).
3. **Plan before pause.** Revalidate every exact running identity and state on both platforms; exclude stopped/unstarted computers. Check save support for all. Persist complete running set and `capturing` journal before pausing any machine. Existing paused checkpoint/setup work is a blocker, not an update-owned save. Suppress health-watch stray-resume/repair on update-owned generations (`engine.rs:1073`; `runtime/update_recovery.rs:79`, `:184`).
4. **Save and hold, one computer at a time.** For macOS, generation-check pause, save RAM, clone disk/auxiliary while still paused, copy model/identifier and exact device config, sync all artifacts, record `saved`. Retain paused VmSlot and native windows but prevent guest input. For Linux, the qualified adapter must atomically capture full memory/disk with required guest flush/integrity and hold execution at that captured point. Record verified member and held runtime identity. No guest advances after its capture until abort/resume. A save failure enters rollback before any runtime release.
5. **Prepared means all saves durable and held.** Persist `prepared`; complete prepare job with `{resuming:[...]}` before publishing finished. Keep admission lease and save ownership alive after the handler returns. A client disconnect does not release them or cancel prepare. The installer waits by job get/event, then records enginePrepared. If the coordinator dies here, its OS install lock disappears. A watchdog checks every 5 seconds with a nonblocking exclusive flock attempt on the same install lock; immediately release a successful probe lock. After 30 seconds continuously finding no coordinator while still prepared, serialize against shutdown and run abort. The installer holds its lock throughout prepare/shutdown/swap/verification, including long capture. Shutdown claims the transaction before the watchdog can abort it. A direct prepare caller without the coordinator therefore gets the same bounded rollback; do not depend on a dead client reconnecting.
6. **Release for update.** Installer calls `engine.shutdown {reason:"update",stopComputers:false}`. Validate all capture refs and held generations, persist `releasing`, detach windows, then release each saved runtime without requesting guest shutdown. On macOS drop the paused VZ instance after detaching its view/delegate safely and wait for storage release (`engine.rs:719`, `:738`, `:1765`). Linux uses the qualified upstream release seam. Record each release and final `released`; flush settings/close engine-owned tunnels. Persist shutdown outcome, enqueue completion, exit 0 and release engine lock. Installer waits for both process termination and lock release, not just socket EOF. PID identity uses recorded process start identity, not a guessed/recycled PID.
7. **Unregister and swap only after exit.** Invoke old canonical bundle's service-unregister command and wait for completion. Apple's [unregister documentation](https://developer.apple.com/documentation/servicemanagement/smappservice/unregister%28%29?language=objc) states it terminates a running service; it must never be the save step. Journal oldUnregistered, rename old bundle to rollback, rename staged bundle to canonical, sync package parent, register through the new canonical bundle, verify launch. Two renames are individually atomic, not one atomic swap; install.json makes the intervening missing-canonical case recoverable.
8. **Restore before ordinary startup.** New engine acquires lock, loads jobs/update state and compatible domain journals. Complete launch-only migration/recovery necessary to read current state, but prevent normal lifecycle recovery/start-at-launch from advancing update-owned IDs first. Validate host/runtime/save/config identities. Restore each computer from immutable captures into a new private working generation, leaving it paused. Keep source captures unchanged so a failed resume can be retried without using disks that have since advanced.
9. **Arm before guest execution.** Persist `resumeArmed` with active working refs and attempt ID before resume; only then resume the exact restored generation. After successful resume commit `resumed` and publish its new state. Transport readiness is a separate bounded retry: changed NAT IP or SSH reconnect is not evidence the guest cold-booted or failed memory restore. Record which sessions/streams need reconnect. Never restore a resumed computer from its old capture after it has made new writes.
10. **Settle.** After all machines resume, persist complete, finish an autonomous recovery job, publish update/computer state, reopen admission, and only then run remaining start-at-launch. Garbage-collect unused capture/working generations after ownership/dependency checks; deleting an old capture must not delete an active restored disk. Remove/sync the resolved journal after cleanup. Installer verifies canonical version plus `engine.state.updatePending=false`, then discards rollback package. A failed resume leaves updatePending and the relevant journal entries; no second update starts until recovery resolves them (`startup.rs:227`; `runtime/update_recovery.rs:274`).

### 3.4 Failure and recovery rules

| Failure point | Required behavior |
| --- | --- |
| Before first pause or unsupported save | Finish prepare error, release guards, leave guests running; no package replacement |
| Partial capture, old process alive | Resume the original held generations using patient calls; failed resume remains journaled and admission remains constrained. Never replace the package after failed prepare |
| Prepared, installer aborts | `engine.update.abort` resumes exact held originals; discard captures only after durable resolution, then reopen admission. Idempotent null if already settled |
| Crash during capture | Missing/non-durable captures cannot preserve that guest's RAM. Reconcile surviving Linux runtimes and only durable saves; report exact failed computers. Keep evidence/artifacts. No invented cold-start recovery |
| Crash during releasing/released | Captures are already durable. New old-version or new-version owner validates them and restores; installer lock/journal controls which package is canonical |
| Swap/register failure | Restore the old signed package and register it, preserving engine journal; old engine restores saved memory. A rollback package is usable only while schema/runtime changes remain backward-readable |
| Restore failure/incompatible host/runtime | Keep capture and error, report retained notice and recovery job outcome; do not cold boot. New package may remain installed while the failed computer is held for resolution |
| Crash after resume but before `resumed` commit | `resumeArmed` is ambiguous. Inspect a surviving runtime and exact restore attempt; if proved running, settle without replay. If owner died or progress cannot be proved, preserve working disk plus capture and report uncertain recovery; do not roll back guest execution automatically |
| One computer resumed, another failed | Leave resumed computer running with its advanced working disk. Retry only unresolved entries. Do not roll back the whole set or reinstall an older engine while that would kill a resumed VM |
| Logout/SIGTERM during transaction | Respect session deadline; preserve durable captures and phase. Pre-save unfinished work can fail; prepared generations release without guest shutdown. Next GUI-session owner resumes only proven durable state |

At bootstrap, reconcile the installer lock/journal before restoring. An old-version engine relaunched by conditional KeepAlive while the installer still owns a prepared/releasing transaction must not resume guests behind that installer. It serves status/get/abort/shutdown with ordinary admission closed, reconciles release of already-dead generations, and lets the coordinator finish the handoff. A new canonical package matching install.json's target restores the saved set. If the coordinator lock is absent, the current validated package takes rollback/recovery ownership. A capturing transaction that lacks complete saves can never authorize swapping. Add this case to the crash tests so an old restart cannot become a competing VM owner.

The resumeArmed ambiguity is unavoidable without an upstream transaction spanning guest execution and host persistence. The design fails visibly at that boundary rather than replaying external effects. Narrow B-30 continuity does not establish exactly-once recovery across every crash. A later engine crash after a macOS entry was durably marked resumed is an ordinary engine crash: its old update capture cannot restore subsequent RAM or be replayed over its advanced disk. Report the lost VM state and preserve artifacts. Existing macOS checkpoint host-build cold boot and current Linux update stop/start are explicitly forbidden in this path (`macos_computers/checkpoints.rs:744`; `runtime/update_recovery.rs:231`; [95 A-6](../95-decisions.md#1-owner-decisions)). Before any launch migration changes schemas, determine whether rollback remains possible; do not delete the old package or run an irreversible conversion before that decision.

### 3.5 Implementation order, tests, risks

1. **One-command platform experiments:** macOS hold/release instead of immediate resume; Linux full capture/hold/release/paused restore. Preserve a counter and survivor PID/boot identity, disk marker and same computer ID across engine replacement. Measure pause/save/clone/release/restore/readiness separately. Port only proved runtime commands; fix the missing reusable hold seam upstream.
2. **Journal state machine:** fake both adapters with deterministic barriers; crash a child process at every artifact sync, journal rename, phase commit, runtime release, resumeArm, resume and result publication. Validate private paths/digests/config, partial save rollback and wrong-generation immunity. Tests must assert no cold-start call and no replay of a resumed disk.
3. **Real Dev macOS transaction:** run old/new signed engine packages, replacement and rollback, with a running guest and no client. Inject ENOSPC, unsupported memory save, restore rejection and installer death. Extend B-30 evidence beyond the first successful restore.
4. **Real Dev Linux transaction:** same task/process/disk evidence, plus guest flush/integrity refusal, surviving detached runtime reconciliation, wrong immutable ID and resumeArm ambiguity. Keep updates with running Linux guests disabled until this passes.
5. **Mixed set and clients:** two kinds, one failure, client app update without engineVersion change, two competing installers, stale installer replay, registration revocation and old-package rollback compatibility. Verify outcomes survive and are discoverable after both planned and injected restarts.

Risks: saved-memory compatibility across macOS host builds, runtime versions, device configuration and encryption keys; delayed auxiliary-storage lock release; large memory-save storage; guest timers excluding downtime; broken host/guest transports after resume; nontransactional external guest effects at resumeArm. Never claim guest clock continuity includes host downtime: B-30 measured otherwise. Full transaction evidence is a release gate, not “80% done” because the save call worked.

## 4. Quit: Keep running / Stop and quit

### 4.1 Files, state, and calls

Create client `QuitCoordinator` beside Fjord's app termination code and Silo `src/desktop/quit.ts`; change Silo `src/desktop/settings.ts`, `shutdown-boundary.tsx`, app menu/tray/status Quit routing and `src-tauri/src/main.rs`. Keep the engine lifecycle controller from §1.7 separate. The current native confirmation/flush/stop path must leave the Tauri process (`settings.rs:879`, `:953`, `:1119`, `:1182`; [05 §6.2](../05-engine-architecture.md#62-client-quit-and-engine-update-are-separate-contracts)).

Client state: `QuitState = idle | reading | prompting | flushing | stopping | disconnecting`, a local prompt generation, captured local `(computerId,name,kind,state)` set, outstanding stop job IDs and per-computer failures. This is client storage, not wire/engine state. Route menu, ⌘Q, Dock, tray and status Quit through one coordinator; repeated requests focus the same prompt. App termination uses the platform's deferred termination reply while it waits.

1. Read fresh **local** `computers.list`. Determine running states from platform enums, not text or remote rows. Include active transitional rows that cannot yet be safely detached/stopped as a visible blocker. Inventory failure leaves the app open with Retry/Keep running; never infer zero running machines from an error. No running computers uses flush/disconnect directly.
2. Ask “Quit Fjord? 2 computers are running: dev, linux-1.” with Cancel / Keep running / Stop and quit. Silo uses its own app name. Cancel releases only the client prompt state.
3. Both exit options drain the client's pending settings write queue and local draft store, then call canonical `settings.flush` for engine writes. A failed save leaves the client open; retain sourced write-protection behavior instead of overwriting protected settings (`settings.rs:183`, `:831`).
4. Keep running calls `engine.disconnect`, awaits its null reply/expected EOF, releases client viewers/transports and exits only that app. Connection loss/crash has equivalent engine detach semantics; already admitted jobs continue. Never call engine shutdown/startup cancel/global transfer cancel ([95 A-2](../95-decisions.md#1-owner-decisions)).
5. Stop and quit sends `computers.stop {computerId}` for the captured local IDs, one request per computer. Each returns a job ID. Await durable outcomes and `computers.changed`; verify with fresh inventory that those IDs are no longer running/transitional. Already-stopped is harmless. Stop refusal or uncertain outcome leaves the client open showing which computer failed. Do not silently escalate to `computers.forceStop`; its use requires an explicit computer action. Show terminal outcomes before acknowledging them.
6. Before disconnect, re-read local inventory. If another client started a different computer during the prompt/stops, return to confirmation with the new names. Don't stop it under the old consent. There is no atomic global client-Quit freeze; that is intentional because clients share an engine. Once the captured set is stopped and the final inventory is clear, disconnect and exit.

Client update/restart/crash never enters Stop and quit automatically. Its updater closes only client-owned resources. Engine-version changes, including a newer candidate bundled with a client update, use §3 under the external coordinator. A same-version client update skips it. Client logout handling must not independently stop VMs; the engine receives its own session-end event ([95 A-2/A-6](../95-decisions.md#1-owner-decisions); [60 §6](../60-connections-settings-services.md#6-app-shell-classification)).

Engine `disconnect` flushes its null reply, disposes caller subscriptions/attachments, closes only that connection, and changes no lifecycle admission flag. Ungraceful EOF runs the same disposal. Selection tokens are keyed by server clientId and invalidated; submitted transfers/jobs keep their owner. Native macOS shared/setup window ownership follows §1.5. No `engine.shutdown.changed` event is emitted for client Quit.

### 4.2 Implementation order, tests, risks

1. **Keep-running tracer:** fake client transport; route all Quit entry points; assert exact flush/disconnect and zero stop/shutdown calls. Two real Dev clients: quitting/crashing/updating one leaves VMs, other client and its viewer operating.
2. **Stop flow:** fixture Linux/macOS platform states; two successful stops, one failure, stale job event, lost socket then get, already-stopped row, new computer started by another client, settings flush failure, repeated Quit and Cancel. 3. **Termination integration:** deferred AppKit/Tauri reply, window close versus Quit, client restart exit path, engine session end. Update existing tests rather than preserve old two-button confirmation behind an adapter.

Risks: final inventory can race another client after it is read; Quit cannot guarantee global absence of running computers without a new device-wide contract. Stop outcomes need independent state verification. A UI-only update must not invoke the old Tauri exit backstop that stops the engine. Product behavior is fixed by 95 A-2, not optional preference logic.
