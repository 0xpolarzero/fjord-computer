Make a project run in a chosen computer, make a Triage rule start an unattended guest job after its automatic checkpoint, and finish Computers on the canonical engine API.

This is a design, not an implementation. It follows [IMPLEMENTATION](../IMPLEMENTATION.md), [README](../README.md), [95 including its overriding amendments](../95-decisions.md#3-amendments-owner-2026-10-13-later), [05's jobs and events](../05-engine-architecture.md#job-contract), all of [70](../70-fjord-needs.md), [P2](p2.md), and [the Linux probes including follow-up](../probes/linux.md). They use `Sources/Fjord/`, not 70's older `Sources/FjordComputer/`. The concurrent P1 Computers files were present and read; their uncommitted contents remain a moving handoff. ## 0. Decisions, boundaries, and dependencies

1. **One click prepares a Desktop session; it does not send the first message.** Router's action opens `claude://code/new` with the alias, guest folder, and prompt. Desktop asks about the connection and the person sends. The Router records “Ready in Claude” until guest evidence identifies the session and turn. No synthetic Send click, host CLI bootstrap/import, or assumed SSH `claude://resume` support. This is the supported path in [70 §1.1/§1.3](../70-fjord-needs.md#13-engine-methods) and [Desktop's SSH link documentation](https://code.claude.com/docs/en/desktop#open-an-ssh-session-from-a-link), rechecked 2026-10-14. An unattended Triage rule uses `guest.exec.start` instead.
2. **The local engine is the only engine connection.** A target contains owner `deviceId` and immutable `computerId`; the local engine routes to that owner. Jobs are keyed by `(deviceId, jobId)`. Names are presentation. There is one engine per Mac **user and channel**, shared by Fjord and Silo, not one across all users or production/development ([95 A-1/A-3/§3](../95-decisions.md); [P2 §1.2](p2.md#12-a-shared-signed-installation-supplied-by-either-app)).
3. **A completed job is retained until shown and acknowledged.** A client disconnect, one hour, or engine restart cannot discard it. Running-process survival is a separate B-37 question. Never treat a progress event or `{jobId}` as completion ([95 §3](../95-decisions.md#3-amendments-owner-2026-10-13-later); [05 §4.2 E](../05-engine-architecture.md#job-contract)).
4. **Fjord owns guest artifacts and workflows; Silo owns generic execution, files, lifecycle, secrets, and durability.** No `router.*`, `triage.*`, capture, clone, screen-lock, or `checkpoints.list` wire method. The latter is a client projection of `computers.list`, already recognized by `EngineClient.swift:441` ([70 §§2–5](../70-fjord-needs.md); [95 A-8/A-9/A-38](../95-decisions.md)).
5. **Missing evidence is a release gate.** B-11 establishes first-party Linux Desktop/alias behavior; B-15 establishes a guest PermissionRequest callback, not the full Fjord plugin; B-16 rejects the local transcript mirror as authoritative; B-17 establishes placeholder/CA inheritance and a controlled API-key substitution test, not actual Claude OAuth bearer rewriting. macOS parity needs P3 tooling, proxy/DNS, guest files/watch, and recorder identity qualification ([70 Open questions](../70-fjord-needs.md#open-questions); [Linux follow-up](../probes/linux.md#follow-up); [40 §5](../40-desktop-display-computer-use.md#5-shared-input-and-recordings-as-proof)).

Implement in this dependency order: P1 schema and UI handoff → generated client and P2 jobs/events → shared installation → one Linux Router project → one Linux Triage job → Computers domain slices → macOS and remote qualification. UI mocks can ship alongside the transport tracer; working feature claims wait for the dependent P3 capability and evidence. P4 does not implement engine adapters advertised by other tracks.

The current skeleton needs three upstream corrections before expansion: `ComputersModel.swift:61` reads/subscribes/reads without a sequence barrier; `EngineClient.swift:413` erases the event envelope and makes `computers.changed` a complete inventory, while the real event can contain just the changed Linux or macOS member; `ComputersModel.swift:221` waits indefinitely for an event rather than using durable job get. A single `activeJob` at `ComputersModel.swift:43` also loses concurrent work. Fix those seams in the shared model, not each panel ([05 event catalogue](../05-engine-architecture.md#event-catalogue); [P2 §2.3](p2.md#23-sequenced-bounded-events-and-resync)).

Subscribe before reading. Track envelope order per subscription/source as P2 specifies; apply the read response as that domain's ordered barrier, discard preceding domain events while still accounting for their sequences, then apply subsequent events. Merge partial changed-state members. On gap, reconnect, or owner loss, invalidate the generation, mark state stale, resubscribe, and reread affected domains, operations, retained outcomes, and notices. File-change events are hints requiring a fresh list/read. A watch ends at computer stop and must be recreated after readiness. Use canonical unsubscribe for the watch subscription according to P1's schema; if that disposal is not defined, settle it with P3-guest before advertising watches, rather than invent `guest.files.unwatch` ([70 `guest.files.watch`](../70-fjord-needs.md#guestfileswatch); [05 §4.2 D](../05-engine-architecture.md#d-pushed-events-a-subscription-method-and-an-event-envelope)).

Persist a change's transport `operationId` before sending. Keep it on uncertain acceptance and reconnect; retries use the same identity and unchanged params. Remote Changes also preserve `startWithinMs`, without extending an expired admission. Request `id`, domain IDs, gate IDs, and job IDs remain distinct. A generic socket retry must never launch a second checkpoint, exec, clone, or upload ([05 §4.1/§4.2 B/E](../05-engine-architecture.md#41-todays-bridge-protocol-protocol-version-5-as-implemented); [P2 §2.2](p2.md#22-id-mappings-gate-links-cancellation-and-restart)).

`EngineJobs` rereads accepted jobs after subscribing and on reconnect so a finish before the start reply is not lost. Discover terminal IDs with `operations.list.unacknowledgedJobIds`. Persist a client result receipt, render the outcome in its result surface, and only then acknowledge on the owner. Receiving or storing an outcome alone does not mean shown. Another authorized client can acknowledge globally; `not_found` must distinguish a locally saved receipt from an outcome the client never saw. Do not label the latter success. `guest.exec.get.firstRetainedSeq` reveals truncated output; show “Earlier output unavailable” rather than synthesizing a complete transcript ([05 `operations.job.get`/`acknowledge`](../05-engine-architecture.md#operationsjobget); [70 `guest.exec.get`](../70-fjord-needs.md#guestexecget)).

## 2. Router: Runs on

### 2.1 Project placement and the visible action

The project picker gains a **Runs on** menu: **This Mac**, then computers grouped by owning Mac and labeled with kind, state, and health. A computer placement requires an explicit absolute guest folder. Show the project root and owner on the project header and every session card. Selecting placement changes future starts; an existing session retains its actual location. Identical `/workspace/repo` paths on two computers are distinct projects. No operation applies the controller's `realpath`, tilde expansion, Finder picker, or existence test to a guest path (`CodeFolders.swift:82–92`, `:395–402`, `:462`; [70 §4](../70-fjord-needs.md#4-clones-inside-a-computer)).

Client storage, implementation choice:

```text
Project { id: UUID, name, githubRepo?, placement }
Placement = thisMac(path) | computer(deviceId, computerId, guestPath)
SessionLocation = thisMac | computer(deviceId, computerId)
SessionIdentity { desktopId?, guestCliSessionId?, location }
PendingDesktopStart { id, projectId, location, alias, folder, prompt, openedAt, state }
```

Store placements in Fjord state through `Models.swift` and `Store.swift`'s existing load/save boundary (`:555`, `:875`, `:1049`); add a launch-only conversion for existing folder projects, with no parallel old/new lookup path. Propagate `projectId`/location through `RouterPointer.swift`, `RouterDispatcher.swift`, `RouterDecisions.swift`, and project/card grouping. `folderKey` is a display/path property, not an execution identity. An explicitly pinned existing session wins its actual location; a project pin starts at that project's placement. Missing computer, offline owner, ambiguous clone, or stale session mapping asks for a specific new target and never falls back to a local clone ([95 §3 No legacy](../95-decisions.md#3-amendments-owner-2026-10-13-later); `RouterDispatcher.swift:639`, `:1498`).

**Start sequence:**

1. Capture project and connection generation. Read fresh inventory/capabilities. If stopped, the same user action starts it with `computers.start` and awaits the job and guest readiness; a failed/unsupported setup shows its concrete blocker. `guest.*` itself never starts a stopped computer.
2. Call `guest.account`. Validate the guest folder with `guest.files.list`; guest home is a config root, not a guessed repo root. Ensure Git/Claude and guest hook prerequisites. On first use install the artifacts in §2.3 before opening a session.
3. Call `guest.sshAlias.ensure {computerId, deviceId, installInclude:true}` on the controller's local engine. The engine owns the generated alias, SSH identity, Include, pinned host keys, and remote ProxyCommand. For Linux, pass `path` only when it meets 50's `/workspace` handoff rules; a different SSH folder goes in the deep link. Do not infer macOS roots or persist a leased IP. A stopped guest, unwritable Include, or unmigrated account is a blocker ([50 `guest.sshAlias.ensure`](../50-access-network-files.md#guestsshaliasensure)).
4. `ClaudeSSHSettings.swift` merges one owned entry into the controller's `~/.claude/settings.json`: `{id: "fjord-<ownerId>-<computerId>", name: "<computer> · <owner>", sshHost: alias}`. Omit key/port overrides so OpenSSH uses the engine config. No `startDirectory` field. Preserve other entries and unrelated settings; refuse malformed types/JSON. Back up the first original, read/compute/re-read/atomic replace with three attempts, following `Forms.swift:719–770`. Share one settings writer with the local form installer so Fjord's own writes serialize. A concurrent external write in the final check/rename window remains a documented local limitation.
5. Build the URL with `URLComponents`/query items: `claude://code/new?ssh_host=<alias>&ssh_folder=<guestPath>&q=<preparedTask>`. Capture the pending start before opening through `Link.open`. Label it **Ready in Claude**, with **Open in Claude** and **Cancel preparation**. Do not claim sent, create a fake `local_<uuid>`, or later relay the same initial prompt automatically.
6. After the person sends, match Desktop metadata to guest registry `hostSessionId` and CLI `sessionId`, restricted to owner/computer and folder. Ambiguous concurrent starts stay unmatched until the person picks. Presence and guest transcript evidence establish a running turn; a URI opened successfully does not. An abandoned pending start can expire as preparation, not as a failed Claude job.

Deleting a computer removes only Fjord-owned `sshConfigs` entries on that controller and calls `guest.sshAlias.remove`; changing a project placement does not remove an alias used by another project/session. On reconnect reconcile deleted computers. An offline controller cannot immediately edit another controller's local Claude config; each reconciles its own records ([70 §1.3](../70-fjord-needs.md#13-engine-methods)).

### 2.3 Guest artifacts and delivery

If missing, `provision-runtime.sh` installs a pinned official guest-compatible Node distribution into the private artifact tree using a verified checksum, through `guest.exec.start`. Version/architecture/checksum manifests ship with Fjord; validate offline/unavailable download and supported guest libc. The upstream [Node download and signed-SHASUMS instructions](https://nodejs.org/en/download) supply artifact provenance; freeze the tested LTS release and hashes when the guest tracer passes. Do not send an interpreter archive as one `guest.files.write` frame. Install the small script/module/config/key through `guest.files.write`; provision larger tools as jobs. This is a proposed packaging choice to qualify in the first guest tracer, not another engine method ([95 A-38](../95-decisions.md); [70 §2.1](../70-fjord-needs.md#21-engine-methods-generic-guest)).

Install order: account/readiness → private artifacts and version manifest → key/config → guest user-scope marketplace/plugin CLI → guest settings CAS → watch folders → enabled marker. Last, verify a real session emits matching presence with `inbox-v1`, and exercise signed delivery, settings application, AskUserQuestion and ExitPlanMode. Desktop's synced device plugin omits hooks; installation in the guest is mandatory, and direct guest `plugin list` alone is insufficient ([70 §2 rows c/d](../70-fjord-needs.md#2-router-internals-that-assume-a-local-session); [B-15](../probes/linux.md#b-15-permissionrequest-in-claude-code-desktop-ssh)).

The signed message format, HMAC, freshness, nonce claim, model/effort and abort semantics remain the existing plugin's. A relay key protects delivery integrity, not secrets from other processes of the same guest user. Copying a checkpoint also copies keys/nonce state: after restore reconcile keys, registry and watches before accepting delivery; a fork gets its own installation identity and key before Router use. Test clock skew because the plugin's signed timestamps and presence leases compare clocks (`Resources/ClaudePlugin/hooks/register.ts:11–38`, `:194–246`; [20 checkpoints](../20-checkpoints-exports-preparation.md)).

## 3. Triage: Run in a computer

### 3.1 Rule action and durable run

Add `ActionKind.runInComputer` with prompt, explicit project/computer placement, model/effort, reviewed permission mode/tool policy, and `recordProof`. The rule editor labels it **Run in a computer** and previews computer/owner/folder, checkpoint policy, prompt, and proof setting. It requires Triage plus the Computers capability, not Router being enabled. Preserve the existing trigger/baseline/deduplication rules at `InboxActions.swift:199`, `:1025–1094`; a newly created action never runs old matching items. ### 3.2 Execution order

1. **Claim durably.** Revalidate the rule/trigger, persist its run and each stable mutation identity, and use the existing `actionsWritten()` gate (`InboxActions.swift:1042–1084`). Deleting/editing the rule or switching Triage off prevents an unadmitted next run. An accepted exec continues until explicit Cancel or computer Stop; tool/window toggles do not masquerade as job cancellation.
2. **Preflight and workspace.** Read owner health, capabilities, inventory, account, guest Claude/tool versions, secret readiness, GitHub repo grant and explicit guest clone. Start a stopped computer only as the rule's chosen target. Await lifecycle and guest readiness. Configure access and clone/fetch through `github.configuration.save` and `guest.exec.start` as needed, with their own job records. Missing macOS Git/LFS/CLT blocks here (B-19). Recheck rule validity before starting the actual run.
3. **Checkpoint immediately before task launch.** Read the owner's `settings.read.automaticCheckpointRetentionCount`. Default is 3. If 0, record “Automatic checkpoints off” and skip by policy; otherwise issue `checkpoints.create {kind:"automatic", name:"Before run: <task>, deleted automatically"}` and await successful `operations.job.finished`/get, retaining `outcome.result.checkpoint.id`. Sanitize/truncate the task portion to satisfy the 1–80 printable-character checkpoint-name contract while preserving the automatic suffix; the full task stays in the run record. Failure, cancellation or uncertain completion prevents task exec. The engine retains/prunes automatic checkpoints; Fjord never deletes manual ones or assumes the UI list has already refreshed ([95 A-18](../95-decisions.md); [20 §1.2.1/§1.4](../20-checkpoints-exports-preparation.md#121-checkpointscreate)).
4. **Proof ready.** If requested, invoke the guest supervisor in §3.4 and await its ready marker before its Claude child starts. Failure to establish requested proof fails before the task, rather than quietly dropping evidence.
5. **Headless task.** Submit `guest.exec.start` with absolute guest Claude/supervisor argv, clone `cwd`, account identity and bounded replay retention. Claude args include `-p <prompt> --output-format stream-json --verbose --permission-mode <reviewed mode>` and validated model/effort options supported by the pinned CLI. No `--bare`, unconditional permission bypass, Desktop URL, or Router peer channel. Use `stdinOpen:false` for this one-shot action; `guest.exec.input` is reserved for an explicitly stream-JSON input run or supervisor control, never shell text ([70 §3](../70-fjord-needs.md#3-triage-unattended-runs); [Claude headless documentation](https://code.claude.com/docs/en/headless)).
6. **Observe and reattach.** Consume `guest.exec.output` with its own payload sequence, distinct from the outer event sequence. Preserve stream-JSON line fragments across event boundaries; stderr is diagnostics. Reattach with `guest.exec.get {sinceSeq}`. Output gaps get an explicit marker. `guest.exec.exited` describes exit; `operations.job.finished`/get supplies durable completion. Parse the final Claude result and error flag as well as process exit; exit 0 alone is not evidence the requested task succeeded.
7. **Finish proof and result.** Supervisor finalizes the recorder, publishes a manifest and exits. Persist a result card with task summary, exit/error, actual reported changes/tests/PR links, checkpoint reference and proof state. Unverified model claims stay labeled unverified. Attach the local finalized video after retrieval. Render the terminal outcome, then acknowledge task/checkpoint/auxiliary outcomes through the shared job layer. Internal checkpoint success can be shown as a visible run milestone; an offscreen completion must remain unacknowledged.
8. **Cancel.** `operations.cancel {jobId, deviceId}` targets the accepted exec. The guest supervisor handles TERM, stops Claude and finalizes the recorder, within the engine's TERM/grace/KILL contract. A cancel before exec admission cancels that workflow's pending checkpoint/provisioning job where supported and never submits task exec. A cancelled recording is partial proof, not success. Lost tracking uses `lost`/uncertain, with no automatic fresh exec ([05 §4.2 F](../05-engine-architecture.md#f-cancellation); [70 `guest.exec.get`](../70-fjord-needs.md#guestexecget)).

### 3.3 Authentication through the secret proxy

Settings offers **Claude token for computer runs**. The person obtains a long-lived token with host `claude setup-token` and enters it in a secure field; Fjord immediately submits `secrets.save` to the owner for the selected computer(s), named `CLAUDE_CODE_OAUTH_TOKEN`, with the qualified destination allowlist. Clear the field; neither Fjord state nor prompts, argv, diagnostics, traces or guest files store the value. For a remote owner the secret travels through the user's SSH route, as 95 A-16 allows. The guest sees only a placeholder and its trusted proxy CA. New environment assignment needs the next boot; show pending/restart state before accepting unattended work ([50 `secrets.save`](../50-access-network-files.md#secretssave); [70 §3](../70-fjord-needs.md#3-triage-unattended-runs)).

**B-17 is not a passing OAuth-auth test.** Its synthetic request put the placeholder in both Authorization and x-api-key; Anthropic rejected x-api-key. The non-allowed echo host retained the placeholder, and `msb exec` inherited placeholder/CA, but no actual successful Claude OAuth request or isolated bearer rewrite was measured. Before enabling this action, capture sanitized actual Claude header names/destinations through the proxy, prove bearer substitution using a controlled endpoint, then run a harmless authorized `claude -p` request with a real token without recording its value. Test non-allowed passthrough, revocation and computer isolation; repeat on macOS after production proxy/DNS/CA lifecycle is ready. Save only redacted evidence alongside these docs ([Linux B-17 initial and follow-up](../probes/linux.md#b-17-allowed-host-substitution-to-apianthropiccom); [proxy remainder](../probes/proxy.md#spec-impact-and-remaining-seam)).

Run under an explicit guest configuration/environment that excludes higher-priority provider credentials, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_API_KEY`, and `apiKeyHelper`, while preserving placeholder and CA. `guest.exec.env` adds values; it is not an environment-unset API. The guest supervisor builds the child environment and controlled config, preserving the installed hook/plugin and approved local MCP/tool policy. Current authentication docs also put a signed-in Claude apps gateway outside the ordinary precedence list; preflight must exclude that provider for this token path. A one-year token enables model requests, not Remote Control or claude.ai connectors, and bare mode ignores it ([authentication docs](https://code.claude.com/docs/en/authentication#generate-a-long-lived-token), rechecked 2026-10-14). Invalid/expired token, wrong provider and missing CA fail before a useful run and get specific remediation.

### 3.4 Guest proof recording and retrieval

Create small `Resources/GuestRuns/run.mjs` and recording wrappers, plus a separately built/signed `GuestRecorder` macOS app target. Install them with guest methods; large bundles use supported Files transfer/job provisioning rather than one oversized small-file write. A guest supervisor owns both task and recorder, waits for readiness, records their IDs/control files, traps exit/TERM and writes final manifests. It continues while Fjord quits or the controller sleeps. A separate host task that stops ffmpeg only after receiving an event would violate that requirement ([95 A-2/A-9](../95-decisions.md); [70 §5](../70-fjord-needs.md#5-guest-proof-recordings)).

Manifest fields: run ID, guest path, kind/container/codec, start/end/duration, dimensions, finalized size, hash, and complete/partial/error. `ProofArtifacts.swift` waits for this manifest using watch/read, then reads the guest movie in bounded ranges into a private local `.partial` file under `Application Support/Fjord/runs/<runId>/`, checking inode/size stability, byte count and hash. Use a conservative 256 KiB raw chunk until schema byte encoding/frame limits are measured; JSON integer arrays can expand bytes considerably. Rename locally only after verification. Persist transfer offset to resume after controller loss; stop/replacement/checkpoint change invalidates the inode and restarts transfer with an explicit reason. A card plays/reveals the local artifact; it never uses a guest path as a local URL ([70 `guest.files.read`](../70-fjord-needs.md#guestfilesread); [05 framing](../05-engine-architecture.md#b-a-persistent-multiplexed-connection)).

Retention is a proposed Fjord policy: cap recording duration/bytes in the supervisor, retain guest proof until a local verified copy exists, then remove only that run's files through `guest.files.remove`. Deleting a run/result explicitly removes its local proof; failed or interrupted transfer leaves guest evidence and a retry action. Do not tie video retention to automatic checkpoint pruning or outcome acknowledgement. Recordings can contain credentials typed into the guest and cannot be generically redacted after capture; show the proof setting in the rule before it is enabled.

## 6. Generated Swift client from silo-api JSON Schema

### 6.1 Tooling choice and source of truth

Use **quicktype-core's JSON Schema input and Swift Codable renderer**, pinned in a small Node tooling package, with a schema-driven Silo renderer extension for wire features the stock renderer cannot preserve. Use its API rather than sample inference. quicktype supports JSON Schema and Swift; its stock Swift integer mapping is `Int`, so unmodified output is insufficient for Rust `u64`/byte/required-null semantics ([quicktype README](https://github.com/glideapps/quicktype#generating-code-from-json-schema), [Swift renderer source](https://github.com/glideapps/quicktype/blob/master/packages/quicktype-core/src/language/Swift/SwiftRenderer.ts), read 2026-10-14). This is a selected tool with a mandatory fixture qualification step, not a claim P1's not-yet-delivered complete schema already compiles.

P1 exports canonical schema **and method descriptors as schema metadata**: method name, kind, request/result refs, job final-result/progress refs, event payload refs, protocol range, schema dialect and digest. Generate typed `Codable` models and async method wrappers from that artifact. JSON Schema describing only envelopes cannot generate all methods; add missing descriptors upstream in `silo-api`, never maintain a second handwritten Swift method registry. Rust/schema/fixtures ship together at a pinned Silo commit/release ([95 A-7](../95-decisions.md); [05 §4.2 H](../05-engine-architecture.md#h-json-schema-from-rust-and-a-generated-swift-client-new-justified-by-95-a-7)).

Renderer requirements are derived from schema, not regex patches to emitted Swift:

- Preserve serde field/discriminator/enum names with CodingKeys, camelCase and snake_case error codes. Decode tagged variants by their discriminator; trial-decoding overlapping structs is insufficient.
- Use `UInt64`/`Int64` from Rust integer format/range metadata, including envelope seq, generation, offsets/inodes, timestamps and byte counts. Preserve arbitrary JSON integer precision, not the skeleton's all-numbers-as-Double `JSONValue` (`EngineClient.swift:366`).
- Preserve omitted versus explicit null where requests use it (`expectedSha256:null` means absent target). Required nullable values such as exitCode must not disappear through synthesized optional encoding. Unknown keys are handled per schema, not silently lost from open objects.
- Follow the schema's actual byte encoding. `Data` synthesized Codable is base64, whereas serde byte vectors can be JSON arrays. Do not assume one because a field is called `bytes`; generate explicit codecs from P1's schema/fixture.
- Keep JSON strings for timestamp/ID fields unless schema semantics require conversion; no locale/date normalization of durable result payloads. Generate safe Swift keyword identifiers while preserving wire names.
- Preserve every progress-source field in a tagged union and each job's final-result type, including data-level failed/cancelled/unknown outcomes. Generate Codable/Sendable value types suitable for the transport actor; UI projections can add Equatable independently.
- Validate schema constructs at generation. Unsupported dialect/ref/union/constraint mapping fails with a location, rather than emitting a permissive Any model and proceeding.

The extension is bounded to these proven wire semantics; contribute general quicktype fixes upstream. Do not select OpenAPI HTTP generation for a Unix framed JSON Schema contract or add a Rust engine FFI to generate wire values. If the first Rust fixture tracer rejects the selected renderer, fix that generator/schema seam before transport integration, without leaving handwritten wire models as a compatibility path.

### 6.2 Files and build step

Create `tools/silo-swift/{package.json,package-lock.json,generate.mjs,swift-renderer.mjs}`, `scripts/generate-engine-client.sh`, `schemas/silo-api/{schema.json,manifest.json,fixtures/}`, `Sources/Fjord/Generated/SiloAPI.swift`, `Generated/SiloMethods.swift`, and `Generated/SiloEvents.swift`. Separate handwritten socket/session machinery (§1) and domain presentation from generated values. Change `EngineClient.swift` to an injected facade/mock of those values, removing duplicate handwritten wire definitions, reduced progress fields and mock-only enum/event shapes. Change `Package.swift` only for target/resources organization needed by generated code; do not run Node or fetch a sibling checkout at app runtime.

Build sequence, proposed command interfaces to implement:

```sh

cargo run --locked -p silo-api --bin export-schema -- --output <artifact-dir>
scripts/generate-engine-client.sh --schema schemas/silo-api --write
scripts/generate-engine-client.sh --schema schemas/silo-api --check

scripts/test.sh
```

The wrapper runs `npm ci` against the tooling lock, validates dialect/manifest and method refs, generates deterministically into a temporary directory and compares/replaces only generated outputs. It records schema/tooling digest without timestamps or machine paths. Commit schema and generated Swift together so plain `swift build` works offline with SwiftPM 5.10/macOS 14. CI and `build-app.sh` run `--check` **before compilation**; it regenerates with locked tooling and fails on drift. Release artifact preparation fetches the pinned schema/engine distribution, checks their matching protocol/schema manifests, then runs generation/check. No release can silently use whatever sibling Silo worktree is on main. Document one-command refresh and fixture provenance in DEVELOPMENT.md.

### 6.3 Order, tests, and risks

1. **Schema tracer:** generate handshake, an error, one inventory, a partial changed event, one setup progress and one checkpoint/exec terminal outcome from P1 schema. Compile. Swift Testing `SiloSchemaTests` decodes Rust-produced fixtures and encodes them back to schema-valid, semantically identical JSON. Byte ordering of JSON object keys is irrelevant; integer/null/bytes/discriminators are not.
2. **Adversarial fixtures:** Rust supplies max UInt64, negative signed values, empty/non-UTF8 byte output, absent versus null hash, keyword fields, variant overlap, unknown enum, malformed/error envelopes, data-level cancellation and all progress sources. Reject unsupported constructs. Prove fixtures in both directions with Rust deserialization/schema validation, not only a Swift self-roundtrip.
3. **Generated methods + socket tracer:** test 4-byte big-endian fragmented frames, 4 MiB rejection before allocation, interleaved events/out-of-order replies, typed errors, protocol mismatch, request identity, disconnect/read retry and no automatic mutation replay. Tool selection alone is not evidence; the release gate is Rust-produced fixture parity plus one real socket lifecycle job.
