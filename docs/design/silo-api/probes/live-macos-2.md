## Item 0: credential_access_denied

Expected: the ad-hoc silod gets `credential_access_denied`, not a Keychain dialog, for the real `org.silo.dev.github` item.
Observed: no dialog on any call (`github.state`, `secrets.list`, `secrets.save`, startup passes). The status was -25293 (`errSecAuthFailed`, "The user name or passphrase you entered is not correct") from the SecItem API. Before `3dddb9f5` it was reported as the generic "Cannot read GitHub credentials from the system credential store." and `secrets.save` as `internal` "Cannot access secrets in the system credential store"; after: `github.state` carries "Allow Silo's engine to use its saved sign-in in the macOS Keychain. (credential_access_denied)" and `secrets.save` fails with error code `credential_access_denied`. Evidence: `80-credential-denied.txt`.

Side effect worth knowing: an ad-hoc bundle's Keychain identity covers the whole bundle. Re-signing after replacing any file in it (even the gateway or the helper) changes the identity, so items the previous silod created (the per-computer proxy CA) become unreadable and must be recreated. Replacing a file in a running bundle without re-signing keeps the running silod's identity but silod refuses to start again ("nested code is modified or invalid"). A stable signing identity (docs/SiloUI-ENGINE.md) avoids all of this.

## Item 5: archive round trip

`65-archive.txt` (first build) and `69-archive-final.txt` (final build).
- Export of a stopped 40 GiB computer: 21.2 GiB `.silo-backup`, "Verified export file", about 12 minutes; the temporary file reached 22.7 GB, so the disk needs about 2x the guest's used space.
- Import as `qa-imp` (about 4 min): the computer arrives needing personalization; Retry setup personalized it, installed computer use, workspace folders and the proxy bootstrap, and it started and had working HTTPS through its own new CA. This needed the helper fix for the stale static service (without it SSH never came up). The retry was proven with the fixed helper swapped into the imported disk by hand because the archive predated the fix; on the final build the export succeeded but the import was cancelled by my disk guard at 32 GB free (archive 23 GB plus source computer plus the imported copy), so the automatic path on the final build is untested.
- Guest facts after import: the marker file `/Users/silo/workspace/marker.txt` is intact; `diskutil info` shows Owners (volume ownership) Enabled on `/` and `/System/Volumes/Data`, as before; **SecureToken is DISABLED** for `silo` after import ("Secure token is DISABLED for user silo", no `;SecureToken;` authority) while the source reported ENABLED. This matches `offline_setup.rs` ("Do not retain ... password-wrapped SecureToken state"): the import rewrites the password verifier offline, which cannot keep a password-wrapped token. Consequence: an imported computer cannot enable FileVault or change the password the secure-token way; decide whether that is acceptable.
- A recommendation: make the import path (which already edits the disk offline) also remove the proxy bootstrap daemon and its network preferences, so archives made before the helper fix still personalize.

## Item 6: engine update save and resume

`64-update.txt` (first build, resume failed twice and `engine.update.abort` resumed in place) and `66-update-v2.txt` (final build). Sequence on a running computer with a background process (`pid 741`, a heartbeat writing the time every second to `/tmp/heartbeat.txt`) and a marker file: `engine.update.prepare` finished in 3 s ("resuming": the computer), `engine.shutdown {reason: update, stopComputers: false}` released the machine without a guest shutdown, silod was restarted, and within about 40 s `computers.list` showed the computer `running` with `updatePending: false` (the recovery thread resumed it). After: the same process is alive (`etime` continues), the file marker is intact, the heartbeat has exactly one 30 s gap (the pause), `uptime` continues from its pre-save value ("up 24 secs" before, "up 4 mins" four minutes of running later), the proxy network is ready again (`Silo network bootstrap ready`, HTTPS 200). `kern.boottime` moves forward by the pause because macOS re-syncs the wall clock on resume; no reboot happened. I restarted the same bundle, not a newer one: a handoff to a newer silod needs a stable signing identity here, otherwise the newer ad-hoc silod cannot read the per-computer proxy CA.
